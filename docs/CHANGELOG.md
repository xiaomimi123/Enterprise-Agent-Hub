## 2026-10-27

**新设备上架验收（员工电脑的清单和自检脚本）：中枢 nginx 413、接入器 0.5.8 自动更新、工作台 0.8.12**
- 来源：员工电脑给的「新设备上架清单」和 `hub-check` 自检脚本。逐项对照源码、在本机复现：
  - **带参考图出图 HTTP 413**：复现了——console-web 的 nginx 没设 `client_max_body_size`，默认只收 1MB，1.9MB 的请求在 nginx 就被拒（小文件 401、大文件 413）。已加 `client_max_body_size 50m`（每张图 ≤10MB、最多 4 张），重建 console-web 后同样的请求都到后端（401）。**这个 bug 是 0.8.10 / 中枢加参考图出图时就有的**，我们当时只用 3KB 的测试图，没测大图。同一条限制还会挡图生视频上传（≤10MB）、知识库 / 技能文件上传。
  - **接入器永远停在装机版本**：确认没有自动更新机制，0.5.6 的「Missing session ID」会一直留在员工电脑上。接入器 0.5.8 加了自动更新：每 6 小时最多问一次中枢（`/api/agent/config` 新增 `agent_version`），中枢上的更新就把装在 `~/.hub-agent` 里的那一份换掉（新文件必须是合法 Python、版本号和宣告的一致、含主要入口，原子替换并留 `.bak-<旧版本>`，失败当没更新；开发时直接跑仓库里的脚本不动；`HUB_AGENT_NO_UPDATE=1` 关闭）。**已在中枢上线（脚本是挂载的，新装的机器直接拿到 0.5.8）**；装机时已是 0.5.8 之前版本的电脑要重跑一次安装命令才会带上这个能力。
  - **启动器「路径写死」警告**：没复现——接入器 0.5.5 起生成的 `open-xhs-workbench.cmd` 用 `%USERPROFILE%`，新装的机器不会有；员工电脑上那条是接入器升级时没重新生成旧文件。
  - **浏览器方式 = none 时点采集没反应**：复现了——点「开始采集」返回成功，队列随后悄悄暂停，原因还写着「请开启后台组件」（已停用的东西）。0.8.12 改成当场 409 + 去哪里改，采集卡片里直接提示并给设置入口。
  - **出图一直「进行中」**：确认是前端轮询只在页面开着时跑；0.8.12 加了服务端每 10 秒取回。
  - 清单里「双击图标不会重启进程」是 0.8.10 的行为，0.8.11 起 `start` 发现旧版本且空闲会自动换。
- 其他：清单里的安装步骤和我们的实际流程不一致——正式流程是 Win+R 粘贴中枢「接入方式」页的一行命令（装 uv、Node、问是否装 CodeBuddy、下载接入器、登录、配置、建桌面图标），PowerShell 里 `%USERPROFILE%` 不会展开（要写 `$env:USERPROFILE`）。`hub-check` 收进 `tools/hub-check/`：修了 Chrome 路径写错（多了一串斜杠）、加了「接入器比中枢旧」的检查。
- 验证：后端 393 项、工作台 442 项通过；对真实中枢验证了 nginx（>1MB 不再 413）和接入器自更新（假装 0.5.7 的副本连真实中枢更新到 0.5.8，备份在、再问被节流）。**没验证**：员工电脑上 0.8.12 的真实表现；后台取回在真实出图任务上的效果。

**接入器 0.5.7：中枢会话失效后桥自动重连（HUB-01）；中枢接口未知字段返回 422**
- 来源：员工电脑的清单（第 9 节 HUB-01、XHS-13 的建议）。桌面 agent 里的中枢工具隔一阵就全部报 `Missing session ID`，重启 WorkBuddy 才好。
- 原因：中枢 MCP 会话在 `hub-mcp` 重启（每次重建中枢都会，这两天重建了很多次）或空闲 30 分钟后作废；0.5.6 的桥遇到 404 只把会话号删掉原样重发，中枢对没有会话号的请求回 400，于是之后每次调用都失败，直到 agent 重启。
- 修复：桥判定会话失效（404，或 400 且提到 session）时，用 agent 当初的 initialize 重新握手、补发 initialized 通知，再把原请求发一次；握手本身失败不递归。中枢 `/api/v1/images`、`/covers`、`/videos` 写错或多传字段返回 422（以前静默忽略：员工那边传 `references` 以为带了参考图，其实被丢掉）。
- 验证：后端 389 项通过（新增桥重连、422 各一项）；**真实对照**——用临时测试账号启动真实的桥连真实中枢，whoami 后重启 `hub-mcp` 再调：0.5.6 复现员工的报错且之后一直失败，0.5.7 自动重连、后续调用都成功；真实 HTTP 传 `references` 返回 422 并指出字段。测试账号和数据已删除。
- 踩坑：第一次重建后容器里还是旧代码（接入器是挂载目录所以显示 0.5.7，后端镜像没更新），真实请求仍是 202，重建后才生效。验证一定要打真实接口，不能只看单元测试和版本号。

**员工电脑升级 0.8.5 后的问题（工作台 0.8.6、接入器 0.5.5）**
- 来源：那台电脑的 WorkBuddy 升级到 0.8.5 后写的升级记录、本地补丁清单（PATCHES.md）和 bridge.json。升级本身成功：网页工作台的 CodeBuddy 自己打开 Edge、读页面、回答，不需要桌面端代跑。
- 对照代码核实后，我们自己的问题有三个：
  - ① **用 CodeBuddy 执行时中枢工具一个都用不了**——`withHubMcp` 只给 Claude Code 补放行名单，CodeBuddy `-p` 模式下白名单外的工具直接被拒。这意味着工作台里的 CodeBuddy 一直没能用上中枢的知识库、技能和 GPU 出图（之前 0.7.4 的测试是在别的路径下跑的，没覆盖到）。
  - ② Windows 上工作台一调用 agent 就**不停闪黑色终端窗口**——服务无控制台启动，子进程没隐藏窗口。
  - ③ 双击启动器 `.cmd` 里写了含中文的绝对路径，cmd 按系统代码页解析时可能把行搞乱。
- 修复：工作台 0.8.6 给 CodeBuddy 按多值参数格式放行中枢工具（幂等，每次运行补回）；所有子进程（codebuddy、where、ffprobe/ffmpeg、npm）隐藏窗口，服务自身启动方式不变，「去登录」的终端照常弹出。接入器 0.5.5 的启动器把用户目录下的路径写成 `%USERPROFILE%\...`，文件变成纯 ASCII。那台电脑 agent 打的本地补丁升级后不用再打。
- 不是我们的 / 待定：Edge 里没登录小红书且「设备登录超限」（员工本人处理）；工作台不能由 agent 常驻（用桌面图标打开）；报告里提到一次 CodeBuddy 内部端口 54590 `EADDRINUSE`，没有足够信息定位，0.8.1 起回复为空时会带出错误输出，再出现时能看到原因；工作台 UI 里的生图 / 生视频按钮走的是第三方直连（apimart / 视频网关），不走中枢 GPU——这是功能缺口，要不要改待你定。
- 验证：工作台 386 项（新增 2 项）、后端 378 项（新增中文用户名启动器为纯 ASCII）通过；已上传 0.8.6，中枢发出接入器 0.5.5。**没验证**：在那台电脑上升级后实际确认不再闪窗、CodeBuddy 能调中枢工具（按你的要求没在开发机上跑）。

- 安装脚本（Windows）：便携 Node.js LTS **一律装进** `HubApps\runtime\node`（不再走 winget / 系统 npm，不需要管理员），CodeBuddy CLI 用它装进同一目录（仍先询问）；没有 uv 时装进 `runtime\uv`；安装出错写 `logs\health-install.jsonl`，接入器登录成功后补报到「应用健康」；连不上中枢时给出明确的话；不再用 `exit`（`irm | iex` 下会把整个窗口关掉，员工看不到报错）。macOS 的 `install.sh` 只加了出错记录和桌面启动器，便携运行环境暂未做。

**Mac 上安装的复盘（`install.sh` 在 agent 里卡死等）**
- 来源：你在另一台 Mac 上让 WorkBuddy 代跑安装后写的复盘。逐条对照代码和服务验证：
  - **属实，已修：脚本在非交互时卡在提问**。`confirm()` 只判断 `/dev/tty` 能否打开，而 agent 拉起的子进程继承了控制终端，能打开却没有人回答，`read` 永远等。又因为脚本是 `curl | sh`（stdin 是管道），复盘建议的 `[ -t 0 ]` 对真实员工恒为假，不能用。改为：要求**标准输出是终端**（agent 会捕获输出）、且没有 `CI` / `CLAUDECODE` / `CODEBUDDY_CODE` / `WORKBUDDY_*` 环境变量，才从 `/dev/tty` 询问；否则跳过，并打印可直接复制的 `HUB_INSTALL_TOOLS=yes curl ... | sh`。
  - **属实，已修：PATH 前置 `~/.local/bin` 让别的工具链留下的 alpha 版 Node 压过正常的 Node**。改为追加；检测到预发布版 Node 会提示；装完 CodeBuddy 后用 `--version` 验证并给出写入 `~/.zshrc` 的命令；脚本开头提示首次登录要改密码；结尾提示 CodeBuddy 的 `/login`。
  - **属实但根因判断不对：控制台一直「正在登录…」**。前端请求用的是相对路径 `/api`，从中枢地址打开时是同源，CORS 白名单不起作用；在预览面板里的页面来源不是中枢，`/api` 根本没转到中枢，放宽 CORS 也没用。因此**没有采纳「放行 localhost:* / null」**：带凭证的跨源放行会扩大攻击面，而且 `redirect_uri` 必须和 Casdoor 里登记的一致，不能按 Host 动态生成。实际做的：前端请求加 20 秒超时和明确提示（「请直接用浏览器打开中枢地址」），不再无限转圈。
  - 未采纳/暂缓：工作台自动选中 Codex 而非 CodeBuddy（需看工作台适配器选择逻辑，另议）；`/healthz`。
- 验证：`sh -n` 语法通过；用桩命令模拟：捕获输出时跳过提问并打印复制命令、`HUB_INSTALL_TOOLS=yes` 走安装、设置 `WORKBUDDY_*` 时跳过；`tsc`、oxlint 通过，已重建前端并确认服务端发出新脚本。**没验证**：真实终端里的交互询问（这里没有 tty），Mac 上完整重跑。
