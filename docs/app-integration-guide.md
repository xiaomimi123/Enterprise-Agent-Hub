# 接入新应用指南：把开源工作台 / 智能体改造成中枢的应用

> 以「小红书运营工作台」为样板总结。每接一个新应用，先读本文判断值不值得接、要改什么，再按清单做；接完把新的经验和限制回写到这里。
> 样板的源码和契约文档：`D:\小红书运自动化运营系统\xhs-workbench1`（独立仓库），尤其是它的 `docs/hub-integration.md`。

## 1. 这是什么模式

我们没有现成的行业名称，内部叫它 **「应用托管 + 对接契约」**（通俗：智能体应用商店模式）：

- **中枢负责**：分发（`apps/` 发布目录）、权限（岗位包勾选「可打开的应用」）、下载校验（签名链接 + SHA-256）、审计（`app.launch`）、给应用里的 agent 提供中枢能力（知识库、技能、出图、模型）。
- **应用负责**：按契约提供启动脚本、数据外置、升级迁移，并在自己的 agent 适配层里接入中枢。

员工说「打开小红书工作台」→ 中枢校验岗位包并写审计 → 本机接入器下载、校验、解压、启动 → 员工在浏览器里使用应用，应用里的 agent 能用中枢的工具。

**不是万能的**：能不能接，取决于下面第 2 节的条件；接入深度分三层（第 3 节）。

## 2. 先判断：这个应用值不值得接

| 检查项 | 通过的标准 | 不通过怎么办 |
|---|---|---|
| **开源协议** | 允许修改和再分发（MIT / Apache-2.0 等）；GPL / AGPL 要核对公开义务；有商用限制的要逐条读 | 不接，或联系作者取得授权 |
| **运行时** | **Node.js ≥ 18**（目前接入器只会用 `node` 启动，见第 9 节） | 用 Node 写一个启动器去拉起它；或先扩展接入器 |
| **形态** | 本机起一个 Web 服务，浏览器访问，启动后能给出一个 URL | 纯桌面 GUI 或需要图形环境的不适合 |
| **体积** | 解压后 ≤ 50 MB、≤ 2000 个文件，无符号链接 | 把大依赖改成首次运行时下载到数据目录 |
| **依赖** | 基础服务零第三方依赖，或能在 `setup` 里自己装 | 避免让员工手动装依赖 |
| **agent 驱动方式** | 有「传入提示词 → 输出后退出」的无界面命令行模式（CLI 模式），或支持收件箱模式 | 没有就只能做第 3 节的 L1 |
| **风险动作** | 能把高风险动作（发布、删除、转账、对外发消息）关掉或收紧 | 不能收紧的不接，或只开放只读功能 |

## 3. 接入的三个层级

| 层级 | 做到什么 | 改造量 | 当前支持 |
|---|---|---|---|
| **L1 分发启动** | 员工能一句话打开应用，权限和审计在中枢 | 小：加 `app.json`、启动脚本约定、打包 | 完整支持（仅 Node 应用） |
| **L2 接入中枢能力** | 应用里的 agent 能用中枢的知识库、技能、出图工具，模型走中枢计量 | 中：适配它背后的 agent（第 6 节） | 按 agent 逐个适配：Claude Code 靠环境变量；CodeBuddy CLI 靠写全局配置 |
| **L3 治理** | 高风险动作技术上关死、分级权限、应用自己的密钥 / 额度也纳入中枢 | 大：逐功能梳理 | 工作台做了只读档 / 测试档；它自带的生图、视频密钥还没统一到中枢 |

建议路线：先 L1 跑通，再 L2，最后按风险做 L3。

## 4. 中枢侧契约（应用要提供什么）

### 4.1 发布目录

```
apps/<应用 id>/
├── app.json           ← 应用描述
└── <版本>.zip         ← 文件名必须等于 app.json 的 version
```

`apps/*/` 被 `.gitignore`，**zip 和 app.json 只在部署机上，不入库**。

### 4.2 app.json

```json
{
  "id": "xhs-workbench",
  "name": "小红书运营工作台",
  "version": "0.7.4",
  "description": "一句话说明",
  "entry": "xhs-workbench/scripts/workbench.mjs",
  "requires": {"node": ">=18", "agent_cli": "codebuddy", "capabilities": ["browser"]},
  "setup_args": ["setup"],
  "start_args": ["start", "--open"]
}
```

- `id`：小写字母、数字、`.` `_` `-`，**必须等于目录名**；`entry` 是解压后包内相对路径，用 `node` 运行；`setup_args` 可省略，**每次打开都会先跑一遍，所以必须幂等**；`start_args` 是启动参数。
- `requires`（可选，写错会让该应用不出现在列表里）：`node` 版本串；`agent_cli` 目前只允许 `codebuddy`；`capabilities` 目前只允许 `browser`，且必须同时声明 `agent_cli`；`playwright_mcp` 可钉版本（`x.y.z`）。
- 校验用的 SHA-256 由中枢按文件内容计算（不用手填）；换 zip 即生效，**不需要重启中枢**。
- 下载走签名链接（有效期 10 分钟）；包路径不安全、含符号链接、解压后超限会被接入器拒绝并丢弃。

### 4.2.1 能力预检（声明依赖，缺什么只拦对应功能）

接入器每次打开应用前按 `requires` 预检：Node/npx、CodeBuddy CLI、中枢模型（`~/.codebuddy/models.json` 里有中枢下发的模型）、系统浏览器（Edge/Chrome/Chromium）、Playwright MCP（未缓存只提示首次要下载）。

- **只拦功能，不拦打开**：缺东西时应用照常启动，接入器把「缺什么、怎么装、是否同意安装」附在返回消息里，审计 `app.launch` 的详情写「缺少能力：…」。
- **询问后才安装**：`hub_agent.py app-doctor <app_id>` 会逐项询问；`--yes` 表示员工已对 agent 同意，才自动执行。只有可自动的项（如 `npm install -g @tencent-ai/codebuddy-code`、同步中枢模型）会被执行，系统浏览器、Node.js 只给手动安装提示，永远不会被自动运行。
- **交给应用**：结果写入 `~/.hub-agent/capabilities/<app_id>.json`（schema 1，不含密钥），并设置环境变量 `HUB_CAPABILITIES_FILE`。应用每次使用时重读；`capabilities.browser.ready === false` 时只拒绝浏览器类功能并说明原因；文件缺失或不合法时不拦。装好后重跑 `app-doctor` 即恢复，无需重启应用。
- 工作台的实现见其仓库 `docs/hub-integration.md`「能力预检」。

### 4.2.2 成果上报（让老板看板看到应用里做成了什么）

应用把关键产出追加写到 `HUB_WORK_OUTBOX` 指向的文件，接入器转发到中枢，显示在控制台「工作看板」。契约（字段、幂等、转发规则）见 [work-report.md](work-report.md)「应用自动上报」。改造应用时要想清楚：哪些状态变化算「成果」（工作台选的是笔记状态变化、对标拆解完成），并只上报标题和状态，不上报正文。

### 4.3 权限与审计

- 控制台「岗位包 → 可打开的应用」勾选后，该岗位的员工才能打开；官方 agent 通道才可用（外部智能体不行）。
- 员工打开应用时写审计：`kind=应用`、`tool=app.launch`，成功带网址，失败带原因，和同一次工作的追踪 ID 串起来。

## 5. 应用侧契约（启动脚本怎么写）

接入器在**包目录下**依次执行（各自限时 90 秒）：

```
node <entry> <setup_args…>     # 初始化，每次都会跑，必须幂等
node <entry> <start_args…>     # 启动，输出一行 URL
```

**输出约定**（接入器靠它判断状态）：

- 必须输出一行 `URL: <地址>`；
- 刚启动输出含「已启动」，已经在运行输出含「已在运行」并返回**同一个** URL（`start` 必须幂等）。

**其他要求**：

- **数据放在包目录之外**（样板用 `~/XHS-Workbench`，可用环境变量改）：换版本、清理旧版本目录（接入器只保留最近 2 个版本）都不影响用户数据。
- **升级**：每次启动检查数据版本，变化时先自动备份再迁移；迁移失败不推进版本、保留备份并在界面显示原因。
- **不被打断**：应用里有定时任务时，接入器**不会强制重启**正在运行的实例；有新版本时只返回现有地址并提示「关闭后再打开即可升级」。
- **停止**：提供 `stop` 命令，供「关闭 XX」使用。
- **缺依赖要给指引**：缺 Node 时接入器已给出安装指引；其他依赖由应用自己检测并说明。

## 6. 接入中枢能力：适配应用背后的 agent

中枢启动应用前会写 `~/.hub-agent/hub-mcp.json`（里面是员工现在用的 MCP 桥，**嵌套模式**，不重复同步技能 / 心跳），并设置环境变量：

- `HUB_MCP_SERVERS_FILE=<该文件绝对路径>`：应用读取后把中枢并入底层 agent 的 MCP 配置；
- `HUB_TRACE_ID`：本次工作的追踪 ID，应用启动的桥会继承，模型调用和工具调用归到同一条链路。

应用要支持这个变量（只保留已知字段、校验类型、限制数量和大小，不能覆盖应用自己的服务）。**没有变量时一切照旧。**

**不同的底层 agent 拿到中枢能力的方式不同，要逐个适配**（样板里的经验）：

| agent | 中枢 MCP 怎么进去 | 模型怎么走中枢 | 要注意 |
|---|---|---|---|
| Claude Code | `--mcp-config` 读 `HUB_MCP_SERVERS_FILE` 的内容，并放行 `mcp__<服务名>` | **未适配**：用 Claude Code 自己的模型设置，不走中枢计量（要走中枢需另写类似 CodeBuddy 的配置写入） | 样板里只有它走环境变量 |
| CodeBuddy CLI | 接入器 `setup` 写 `~/.codebuddy/.mcp.json`（全局，不靠环境变量） | `~/.codebuddy/models.json` 写入岗位包允许的模型，`url` 要完整的 `/chat/completions` | 无人值守要放行 `DeferExecuteTool`；`--allowedTools` **每个工具名单独一项**；Windows 上提示词必须走标准输入，否则多行会被 .cmd 垫片截断 |
| WorkBuddy 等桌面 agent | 一键接入写它的 `mcp.json` | 用它自己的模型（不走中枢，不计量） | 只能走收件箱模式，**按设计不能开浏览器** |

适配新 agent 时逐项确认：怎么传提示词（参数 / 标准输入）、无人值守没有权限弹窗时怎么放行、工具名格式、MCP 配置文件在哪、模型怎么指定、输出怎么解析。

## 7. 治理：高风险动作怎么关

- **写进配置，不靠提示词**。提示词可以被忽略，权限不会。样板的做法：
  - 只读档（默认）：浏览器写类工具（点击、输入、上传、脚本等）全部禁用，被禁的工具对 agent **不可见**；
  - 测试档：放开交互工具，但仍禁上传和脚本，并屏蔽发布入口域名；切换命令 `browser-mode readonly|test`，测完必须切回。
- **平台合规类硬约束要落成技术手段**：样板的硬约束是「自动化只能只读分析，不能自动发布」。
- 默认值取最稳妥的一档；放开权限需要使用者明确授权。
- 关键写操作都留审计，详情里不含密码和密钥。

## 8. 改造一个开源项目：逐步清单

1. **读协议、评估**：按第 2 节逐项打分，不通过的先停。
2. **跑通原项目**：在本机按它自己的文档跑一遍，确认没有隐藏依赖。
3. **最小包装（L1）**：写 `scripts/<启动脚本>`，实现 `setup` / `start` / `stop`，数据外置，输出 `URL:`；**尽量只加包装层，少动上游源码**，改动集中、写清楚，方便以后跟上游。
4. **打包上传**：升版本号 → 打包 → 放进 `apps/<id>/` → 改 `app.json`（第 10 节）。
5. **验收 L1**：给一个岗位包勾选应用，员工说「打开 XX」，能下载、校验、启动，审计里有 `app.launch`，再说一次返回同一个 URL。
6. **接入中枢（L2）**：支持 `HUB_MCP_SERVERS_FILE`；适配它背后的 agent（第 6 节）；验收：在应用里让 agent 调 `whoami` 和一个知识库检索，审计里能看到。
7. **治理（L3）**：列出所有高风险动作，逐个决定关闭 / 收紧 / 需确认；做只读档；写测试证明被禁的工具真的不可用。
8. **真实环境验证**：用真实的 agent、真实账号跑一遍核心流程，不能只看单元测试；记录没验证到的部分。
9. **写文档和更新记录**：应用自己的 `CHANGELOG`；中枢这边 `docs/CHANGELOG.md` 记一条；本文如有新经验回写。

## 9. 当前的限制和待办（接第二个应用前先看）

- **只支持 Node 应用**：`launch_app` 里写死用 `node` 启动，`requires` 里只检查 Node（能力预检已支持 `agent_cli` / `capabilities`，但取值白名单目前只有 `codebuddy` / `browser`）。要接 Python / 其他运行时的应用，需要扩展 `app.json`（如 `runtime` 字段）和接入器。
- **接入器里还有工作台的特例**：`launch_app` 里找 `xhs-workbench/SKILL.md`、判断输出里是否含「尚未配置」、提示文案写的是「工作台」。接第二个应用前要抽成应用自己声明的字段。
- **`HUB_MCP_SERVERS_FILE` 只对 Claude Code 生效**：其他 agent 要另写适配（CodeBuddy 靠全局配置）。
- **应用自带的模型密钥没统一**：工作台的生图、视频密钥（APIMart、视频网关）仍由应用自己管，额度和审计不在中枢；契约里的方向是逐步改走中枢的 `generate_image` / `generate_video`。
- **知识库是两套**：中枢 `vault/` 和应用自己的知识库未打通，先分别使用。
- 应用包不入库，新服务器部署需要手动放 zip（建议在应用仓库的 GitHub Releases 里留存每个版本的 zip）。

## 10. 发布新版本（每次上传都必须升版本号）

1. 应用仓库：改版本号（样板在 `server/version.mjs`）；在应用自己的 CHANGELOG 顶部加条目；提交（包由 `git archive` 生成，未提交的不进包）。
2. 跑测试，再打包（样板：`node tools/package.mjs`，会打印文件数和 SHA-256）。
3. 复制 zip 到中枢仓库 `apps/<id>/<版本>.zip`，把 `app.json` 的 `version` 改成同一个版本（**文件名必须等于 version**）。不用重启中枢。
4. 验证：中枢读到新版本、SHA-256 与打包时一致（可在容器里用 `apps.list_apps()` 和 `apps.sha256_of()` 核对）。
5. 在 `docs/CHANGELOG.md` 和 `CLAUDE.md` 记下当前上传的版本。

已在运行的实例不会被强行重启；员工下次打开时拿到新版本。
