# 方案 B：把小红书运营工作台做成 DeepSeek Harness（DSH）的插件（草稿，含验证结果）

> 状态：**可行性已在本机验证（2026-10-27）**，等你决定是否按这个方向做。
> 取代 `桌面应用方案.md` 里「自己做 Electron 应用 + 选开源 agent 底座」的部分；那份文档里关于签名证书、浏览器、分阶段的思路仍可参考。
> 验证方式：全程用**单独的测试环境**（独立 `DSH_HOME`、单独装的 CLI、临时测试账号），**没有动你本机 `~/.dsh` 和已安装的桌面版**；测试账号和数据已删除。

---

## 1. 结论

**可以做，而且比「自己做桌面应用」省掉最大的几块**：agent 循环、上下文压缩、重试、MCP 客户端、模型适配、聊天界面、会话管理、技能、计划模式、审批界面，DSH 都已经有了，MIT 协议。我们做的是一个**插件（bundle）**：接中枢的模型和 MCP、锁住不该有的内置工具、加上小红书工作台的工具和界面。

**但有四件事必须先说清楚**，它们决定了怎么交付，也是这个方向的主要风险（第 4 节）：
1. DSH 目前是**开发者预览版**，官方仓库写着会有不兼容的改动；
2. 桌面版**走 nightly 通道、并且有强制更新机制**，我们没法固定版本；
3. 默认带**向 DeepSeek 上报的遥测**，要在我们的 bundle 里关掉；
4. 浏览器自动化这一块 DSH 没有现成答案，要单独定。

我的建议：**用 DSH 的运行时和插件机制，但交付我们自己固定版本的发行包**，不依赖 DeepSeek 官方桌面版的自动更新（第 5 节）。

## 3. 验证中发现的问题

1. **22K token 的固定开销**：一个很简单的请求，界面显示「用量 22K tok，缓存命中 49%」。DSH 的系统提示词加上 17 个 MCP 工具的描述很大。按人计量的月度额度会被消耗得比较快。对策：只开放需要的 MCP 工具、精简系统提示词、依赖缓存。要在真实任务上再量。
2. **MCP 令牌会过期**：员工令牌 24 小时有效，写在配置里是静态的。长时间开着的会话会在第二天断。需要一个**本地网关**：自动续期令牌、会话失效自动重连（就是接入器 0.5.7 修的那类问题），MCP 指向本地网关，不带鉴权头。
3. **登录和领取配置要重做成 Node 版**：现在是 Python 接入器（PKCE 登录、enroll 领模型 key、续期）。插件里要有对应的服务端部分，登录后把模型 key 和提供方配置写进 profile。
4. **`dsh web` 会自动打开默认浏览器**（要加 `--no-open`）。
5. **安装插件要用 pnpm**，而 npm 版 CLI 不带。桌面版自带 pnpm；我们的发行包要自己带，或者**直接预置好 profile 目录**（我们自己装好再整体下发），员工电脑上不需要跑 `dsh plugin add`。
6. **你本机的桌面版被改过**：安装目录里有 `app.asar.dshpurge-prev`、`dsh.cmd.dsh-purge.bak`，装了一个叫 `dsh-purge` 的插件（介绍是「破甲」，让模型绕过限制）。**我没有用它做测试**，也不建议拿它做员工分发的基准。给员工的发行包必须是干净的。

## 4. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **预览版，接口会变** | 仓库首页：「developer preview … THERE WILL BE COMPATIBILITY-BREAKING CHANGES」；npm 上 `latest` 是 `0.2.1-rc.2`、`next` 是 `0.2.1-rc.4`；社区教程注明基于 8 月中旬的预发布代码 | **固定版本**：发行包里锁定一个具体版本，升级前跑我们自己的回归任务集再换；`engines.dsh` 写死范围 |
| **桌面版强制更新** | 桌面版 `app-update.yml` 是 `channel: nightly`，`package.json` 里有 `dshMandatoryUpdatePolicy`（来源 `harness.deepseek.com`）。DeepSeek 可以推送强制更新，我们没法固定 | **不让员工用官方桌面版**，用我们固定版本的发行包（第 5 节） |
| **默认遥测** | 默认配置里 `session-telemetry-otel` 指向 `https://dsh-otel-collector.deepseeksvc.com/v1/logs`（模式 `FEEDBACK_ONLY`，用户提交反馈时才发）；桌面 profile 另有产品分析（`product-analytics`、`desktop-product-telemetry`）。我们的资料（对标、品牌素材）不能外发 | bundle 里把 `otel`、`session-telemetry-otel`、`desktop-product-telemetry`、`product-analytics` 都设为 `disabled`，并在回归里抓包确认没有外发。**这一条还没验证关闭是否真的生效** |
| **界面是通用 agent 界面** | 界面带文件、终端、子 agent、计划模式等开发者功能，品牌是 DeepSeek | 能关的插件关掉（`ui-sidebar-terminal`、`ui-sidebar-files` 等）；品牌和定制界面能改到什么程度还没验证 |
| **员工自己改配置** | DSH 有设置页和插件管理，员工可能把内置工具又打开 | 关掉 `config-editor`、`plugin-manager` 及对应界面；**是否能真正锁死还没验证** |
| **浏览器自动化** | DSH 没有现成的、可控的浏览器方案 | 见第 6 节 |
| **依赖 DeepSeek 的项目走向** | 它是 DeepSeek 自己的开源项目，但我们要跟随预览版的节奏 | 固定版本、自己维护发行包，核心逻辑放在我们的插件和本地网关里，尽量少依赖 DSH 的内部接口 |

## 5. 交付方式（建议）

**不要让员工装官方 DeepSeek Harness 桌面版**（nightly、强制更新、遥测、被你说的那些问题），改成我们自己的发行包：

```
小红书运营工作台 发行包（从中枢下载，沿用现在的「应用」分发和 HubApps 目录）
├─ 便携 Node（现有安装脚本已经会装）
├─ @deepseek-ai/dsh 固定版本（含 pnpm 或预置好的 profile）
├─ 我们的 bundle：中枢网关 + 工具 + 锁定的内置工具 + 关闭遥测
├─ 现有工作台服务（内容、素材、排期、发布包、出图出视频），作为本地服务
└─ 启动器：启动 dsh web --no-open，用 Edge 应用模式（--app=）打开窗口
```

- 窗口用 Edge 的应用模式，看起来像一个独立应用，不需要自己做 Electron，也**不需要签名证书**（沿用现在的安装脚本，是 PowerShell + 便携包）。
- 更新沿用中枢现有的应用分发：中枢上放新版本，员工下次打开自动换。
- 员工电脑上**不再需要**：uv、Python、WorkBuddy、CodeBuddy CLI、Edge 扩展。

## 6. 浏览器自动化

这是目前没有答案的一块，要分开说：

- DSH 内置有 `ui-sidebar-browser`（右侧浏览器面板）；社区有 `dsh-browser`（Chrome 侧边栏扩展，让它操作当前页）、`dsh-better-browser`（驱动真实浏览器）。**能力、能不能按动作加节奏和额度限制，都还没验证。**
- 我们之前定的原则不变：**只读、节奏和额度由代码强制、不做伪装、遇风控自动停、先用测试号**。所以浏览器动作必须经过我们自己的工具（每个动作前过 `pace.mjs` 的规则），不能让 agent 直接拿到一个自由的浏览器。
- 在网页模式（Edge 里开的页面）里，没有「内嵌的、由应用控制的浏览器」。要么用 DSH 的浏览器面板（待验证），要么做我们自己的受控窗口。

**建议：第一版不含浏览器页面读取**，先把文案、出图、视频、发布包、知识库、排期做成稳定可用的版本；第二阶段再验证浏览器方案。

## 7. 分阶段（修订）

| 阶段 | 做什么 | 验收 |
|---|---|---|
| **0. 可行性** | ✅ 已完成（第 2 节） | — |
| **1. 网关与锁定** | 本地网关（PKCE 登录、enroll、令牌续期、MCP 会话重连）；bundle：中枢模型和 MCP、锁定内置工具、关闭遥测（并抓包验证）、关掉配置和插件管理界面 | 员工只能用中枢能力；抓包没有外发；令牌过期后会话自动恢复；固定版本 |
| **2. 工作台能力做成工具** | 把现有工作台的服务（笔记、素材、排期、发布包、出图出视频、对标检查点和采集账本）以工具的形式暴露给 agent；现有网页界面作为第二个窗口保留（先不重写界面） | 员工用对话完成「按知识库写笔记 → 出封面 → 套用 → 下载发布包」，10 次里成功 ≥8 次 |
| **3. 发行包与分发** | 启动器、Edge 应用模式窗口、中枢分发和自动更新、装机自检 | 3～5 个员工试用一周：装机 ≤10 分钟，不需要 WorkBuddy / CodeBuddy |
| **4. 界面整合与浏览器** | 评估把工作台页面做成 DSH 的客户端插件（侧边栏面板）；验证浏览器方案 | 单独评审后再定 |

量级：阶段 1～3 大约 **2～3 周**（比「自己做桌面应用」少，主要省在 agent 底座和聊天界面）；阶段 4 视结果而定。
