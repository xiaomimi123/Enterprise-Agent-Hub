# 发行包 + 安装前自检方案（草稿）

> 状态：草稿，待用户确认后再动代码。写于 2026-10-28。
> 要解决的问题：**有的员工电脑能装能启动，有的不行，每台原因不同，只能靠员工反馈一台一台排。**

## 1. 先说结论

- **方向：做「自带环境的发行包」，不做 Docker。** Docker Desktop 在员工 Windows 上要开 WSL2 / 虚拟化，很多公司电脑没开或装不上，反而比现在更难装；采集还要用员工真实 Edge 里的 WorkBuddy 扩展，容器里碰不到。
- **现状已经有一半：** `agent/install.ps1` 已经把便携 Node.js、uv、CodeBuddy CLI 装进 `%USERPROFILE%\HubApps`，不要管理员权限。问题是它**边装边从外网下载**（nodejs.org、npm、uv、Python），任何一步在某台电脑上被拦（网络、杀软、代理、策略）就失败，而且失败时我们看不到原因。
- **要补的是三件事：**
  1. **安装前自检（preflight）**：装之前只读检查这台电脑，能装就装，不能装就**说清楚缺什么**，不是装到一半报错。
  2. **离线发行包**：运行时全部由中枢提供，安装过程不再访问外网。
  3. **失败回传与干净机器验收**：每次失败带着错误码回到中枢的「应用健康」页；每次发版在干净机器上完整走一遍。
- **边界：** CodeBuddy CLI 的登录、WorkBuddy 的浏览器扩展是别人的软件，打不进包，只能检查并给明确提示。

## 2. 现状：每项依赖从哪来

| 依赖 | 现在怎么来 | 在员工电脑上的风险 | 能不能自带 |
|---|---|---|---|
| Node.js | 安装时从 nodejs.org 下载便携 zip（校验 SHA-256） | 外网被拦 / 慢 / 代理 | **能**，放进发行包 |
| uv + Python（接入器 `hub_agent.py` 用） | 安装时下载 uv，再由 uv 取 Python | 同上，且杀软常拦 uv | **能**，嵌入式 Python 或直接把接入器改成 Node（见 §7） |
| CodeBuddy CLI | `npm install -g` 从 npm 源拉 | npm 源被拦、node-gyp 之类 | **能**，把装好的 `node_modules` 放进包 |
| 接入器 `hub_agent.py` | 从中枢下载 | 只依赖中枢，稳 | 已经是中枢提供 |
| 小红书工作台 | 从中枢 `apps/xhs-workbench/<版本>.zip` 拉 | 只依赖中枢，稳（曾因 nginx 1MB 上限 413，已修） | 已经是中枢提供 |
| CodeBuddy 登录 | 员工自己登录 | 与 WorkBuddy 共用凭据存储，偶发读不出 / 写不进 | **不能**，只能检查 + 给处理步骤 |
| WorkBuddy 桌面 + Edge 扩展 | 员工自己装 | 版本不一、扩展没启用、Edge 不是默认浏览器 | **不能**，只能检查 |
| 员工自己的环境 | — | 用户目录含中文、PATH 被污染、WorkBuddy 注入 `NODE_OPTIONS` 等钩子变量 | 启动时洗环境（0.8.14 已补一部分） |

已知的、会随机器不同而发生的失败（来自已有记录，不是猜的）：沙箱拦 `iex`；PATH 被覆盖；无 winget；用户目录含中文导致批处理出错；CodeBuddy `missing-key` / `safe-delete` 登录失败；WorkBuddy 注入变量导致端口冲突或要求托管凭据；中枢 nginx 请求体上限；员工把工作台放进被沙箱限制的目录。

## 3. 总体设计：四层

```
L0 安装前自检（只读）   → 能不能装？不能就列出缺什么、怎么办
L1 离线发行包           → 装的时候只访问中枢，不访问外网
L2 安装后验证           → hub-check --deep：真跑一次，不是「文件在」就算过
L3 失败回传             → 带错误码上报中枢「应用健康」，管理员能直接看到哪台为什么失败
（贯穿）干净机器验收    → 每次发版在 Windows 沙盒 / 新机上完整走一遍，通过才上架
```

## 4. L0 安装前自检（preflight）

**形式：** 一个只读脚本（`preflight.ps1`，纯 ASCII，随 `install.ps1` 的入口一起下发，也能单独运行）。**不改任何东西**，输出每项 PASS / WARN / FAIL，FAIL 时给出一句人话和处理办法，最后给一个错误码汇总。`install.ps1` 开头先跑它，有 FAIL 就停，不往下装。

检查项（每项对应一个已发生或高概率的失败）：

| 类别 | 检查 | FAIL / WARN 时怎么办 |
|---|---|---|
| 系统 | Windows 10 1809+ / 11；64 位 | FAIL：不支持 |
| 系统 | PowerShell 版本、`ConstrainedLanguage` 模式、执行策略（`Restricted` / `AllSigned`） | FAIL 并给 `powershell -ExecutionPolicy Bypass -File` 的办法 |
| 用户目录 | 路径含中文 / 空格 / 超长（> 80 字符） | WARN：批处理易出错；建议 `HUB_APPS_ROOT` 指向纯 ASCII 目录 |
| 磁盘 | 安装盘剩余空间 ≥ 1.5 GB；目标目录可写（真写一个临时文件再删） | FAIL |
| 权限 | 不需要管理员；检查是否被「受控文件夹访问」拦写 | WARN |
| 网络 | 中枢 `/api/agent/config` 可达、延迟；**只检查中枢**（离线包后不需要外网） | FAIL：写明地址和这台电脑看到的错误 |
| 网络 | 系统代理 / 环境代理是否指向已不存在的本机端口 | WARN：给出清掉的办法 |
| 端口 | 登录回调 `27891`、工作台 `17890–17910` 是否被占用 | FAIL / WARN，指出占用进程名 |
| 杀软 | Defender 是否有对 `HubApps`、`node.exe` 的拦截记录（读事件日志，只读） | WARN |
| 浏览器 | Edge 是否安装；WorkBuddy 扩展是否存在（只检查，不启用） | WARN：采集不可用，其他功能照常 |
| 已有软件 | 是否已装 WorkBuddy、版本；是否已装 CodeBuddy CLI、版本 | 信息 |
| 环境污染 | 当前进程是否带 `WORKBUDDY_*` / `CODEBUDDY_*` / 指向 workbuddy 的 `NODE_OPTIONS` 等 | WARN：提示「请从自己的 Win+R 窗口运行，不要让 agent 代跑」 |
| 沙箱 | 当前是否在 agent 沙箱里（`iex` 被拦的特征） | FAIL：给出 Win+R 一行命令 |

**输出：** 控制台人话 + 一个 `preflight.json`（机器 id、各项结果、版本信息，**不含用户名以外的个人信息**），同时 POST 到中枢的应用健康接口（用已有的 `HUB_HEALTH` 机制，可关）。

**验收标准：** 在故意搞坏的环境里（改执行策略、占用 27891、用户目录放中文、断网只通中枢、带 `WORKBUDDY_*` 变量）每种都得到**正确的 FAIL / WARN 和处理办法**；在干净机器上全 PASS。

## 5. L1 离线发行包

**目标：** 安装过程只访问中枢（一个地址、一个域），员工网络只要能打开控制台就能装。

**内容（一个 zip，由中枢构建并托管，`/api/agent/bundle/<版本>.zip`）：**

```
bundle/
  manifest.json           版本、各组件版本、SHA-256、构建时间
  runtime/node/           便携 Node.js（固定一个 LTS 版本）
  runtime/codebuddy/      预装好的 @tencent-ai/codebuddy-code（固定版本）的 node_modules
  runtime/python/         嵌入式 Python（或见 §7：把接入器改成 Node，就不需要）
  connector/hub_agent.py  接入器
  apps/                   岗位包里的应用 zip（可选，也可以首次启动时从中枢拉）
  preflight.ps1  install.ps1
```

**做法：**
- **固定版本，不跟最新：** Node、CodeBuddy CLI、嵌入式 Python 的版本写在 `manifest.json`，升级由我们在干净机器上验证后发新包。CodeBuddy 官方更新可能再引入问题，所以**员工机上的 CLI 不自动升级**（可以关掉它的自更新，或安装后锁定目录为只读——先验证再决定）。
- **校验：** 安装时按 `manifest.json` 校验每个组件的 SHA-256，不一致就停并回传错误码。
- **构建：** 在中枢仓库加 `tools/build-bundle/`（脚本），在有外网的构建机上执行一次，产物放到中枢的静态目录；不进 git（和 `apps/` 一样）。
- **安装目录：** 仍是 `%USERPROFILE%\HubApps`，用户目录含中文时改用纯 ASCII 目录（preflight 提示）。
- **回滚：** 新版本装到 `runtime.<版本>/`，成功后切换指针，旧版本保留一个；失败时自动回退。

**不做的事：** 不把 WorkBuddy、Edge 扩展、CodeBuddy 的登录打进包；不做 Docker；不做 MSI / 签名安装包（用户已决定不买证书，沿用 Win+R 一行命令）。

**验收标准：** 在**完全断开外网、只通中枢**的机器上，一行命令装完，`hub-check` 全部通过。

## 6. L2 / L3：安装后验证与失败回传

- **L2：** 安装结束自动跑 `hub-check --deep`（已有）。要点是「真跑」：用 `codebuddy -p "只回复：PONG"` 实测，而不是只看文件在不在；结果不是 PONG 就把「采集不可用」明确写进交付单，不要让员工以为装好了。
- **L3：** `install.ps1` 的每一步失败都带**固定错误码**（现有 `Write-Health` 机制，例如 `NODE_MISSING`），统一规范：`PREFLIGHT_*`（自检）、`BUNDLE_*`（下载 / 校验）、`INSTALL_*`、`LOGIN_*`、`RUNTIME_*`。控制台「应用健康」页按错误码聚合，管理员能一眼看到「5 台电脑卡在 `PREFLIGHT_PORT_27891`」。
- **员工侧话术：** 每个错误码在控制台「接入方式」页有一条对应的处理办法（已有同类页面，扩充即可）。

## 7. 一个需要你定的取舍：接入器要不要继续用 Python

现在 `hub_agent.py` 依赖 Python（由 uv 取）。这是员工电脑上**另一条外网下载链**，也是 `uv` 被杀软拦、Python 取不到的来源。两个选择：

- **A：继续 Python，发行包里带嵌入式 Python。** 改动小，包多约 25 MB。
- **B：把接入器改写成 Node（工作台本来就在 Node 上跑）。** 少一个运行时，登录、令牌续期、MCP 代理逻辑在 `dsh-plugin/src/gateway` 已经用 Node 写过一版并通过真实中枢测试，可以直接复用。**但是**接入器现在是线上已经在自动更新的东西（0.5.8 起员工机会自己替换），改写要非常小心，需要完整回归。

建议：**先做 A，把发行包和自检落地；B 作为后续，等 A 稳定后单独评估。**

## 8. 干净机器验收（必须有）

开发机什么都装好了，永远复现不了员工电脑的问题（CLAUDE.md 里已记）。每次发新包前：

1. **Windows 沙盒脚本**（`tools/clean-room/*.wsb` + 脚本）：每次启动都是全新系统，自动执行「Win+R 一行命令 → 登录（测试账号）→ hub-check --deep」，输出报告。需要 Windows 专业版并启用沙盒功能（你的电脑是 Windows 10 Pro，可以用）。
2. **「让 WorkBuddy 代跑」那一遍：** 手工，在一台干净的电脑上，因为沙箱拦截行为只有真机能看到。
3. **故障注入矩阵：** 自检里列的每种失败各做一次（断外网、改执行策略、占端口、中文用户目录、WorkBuddy 环境变量），确认提示和错误码正确。

**注意：** 你之前说过浏览器相关链路不要在开发机上测，所以沙盒验收只覆盖安装、登录、中枢链路、CLI 的 PONG；浏览器采集由你在员工机上手测。

## 9. 分期

| 期 | 内容 | 产出 | 估计 |
|---|---|---|---|
| 1 | `preflight.ps1` + 错误码规范 + 回传 + 控制台错误码对照页 | 装之前就能分清能不能装；失败原因集中可见 | 小 |
| 2 | Windows 沙盒干净机验收脚本 | 每次发版有客观通过 / 不通过 | 小 |
| 3 | 离线发行包（方案 A：带嵌入式 Python）+ 校验 + 回滚 | 员工网络只要通中枢就能装 | 中 |
| 4 | 固定 CodeBuddy CLI 版本、评估关闭其自更新；评估接入器改 Node（§7-B） | 减少版本漂移 | 中，需评估 |

建议**先做第 1、2 期**：不改安装流程本身，风险最低，做完立刻能让「有的电脑装不上」变成可见、可分类的问题；第 3 期再决定要不要做。

## 10. 不确定 / 没验证的

- 嵌入式 Python 在受限电脑上能否可靠运行（杀软是否拦 `python.exe` 在用户目录执行）——没验证。
- 关闭 CodeBuddy CLI 自更新的具体办法——没查。
- Windows 沙盒能否复现「WorkBuddy 代跑」的沙箱拦截——不能，这项只能真机手测。
- 员工机上 Defender 事件日志是否普遍可读（可能需要权限）——没验证，读不到就退成 WARN「无法检查」。
- 上述估计是量级，不是工时承诺。

## 11. 需要你决定

1. 分期顺序是否按「先 1、2 期」？
2. 接入器改不改 Node（§7）：先保持 Python（推荐）还是直接排期改写？
3. 发行包是否接受由中枢机器构建并托管（占几百 MB 磁盘）？
