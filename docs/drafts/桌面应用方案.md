## 1. 为什么要改

这几天的问题按来源分：

| 来源 | 例子 | 打成一个应用后 |
|---|---|---|
| WorkBuddy 沙箱 | 拦 `iex`、`reg.exe`；结束它拉起的程序；给子进程注入 60 个 `CODEBUDDY_*` 变量导致端口冲突 | **没有这层**：应用不在任何 agent 里面运行 |
| CodeBuddy CLI | 要单独登录；登录凭据和 WorkBuddy 桌面共用一份存储，出现「登录完仍未登录」 | **不需要**：应用直接调中枢的模型网关，用员工自己的模型 key |
| 运行环境 | uv、便携 Node、PATH、`npm.cmd`、中文用户名、启动器路径 | **打在包里**：一个安装程序 |
| 版本 | 接入器和工作台各自一个版本，接入器以前不会自己更新 | **一个版本号**，应用自己从中枢更新 |
| 浏览器自动化 | Playwright 带自动化特征；WorkBuddy 插件链条长（扩展、浏览器操控、登录）；品牌号被平台提示 | **改成人在前面、一次读一页**（见第 5 节） |
| 我们自己的缺陷 | nginx 413、会话失效、采集提示误导 | 不受影响，照常修 |

前五类是这几天的主要成本，而且每台新电脑都会再遇到一遍；最后一类是正常的开发问题，修一次就好。

## 2. 要做成什么样

一个 Windows 安装包 **「小红书运营工作台.exe」**：

- **按用户安装**（装到 `%LOCALAPPDATA%\Programs`），不需要管理员权限。
- 打开后用**公司账号登录**（和现在的接入器一样，浏览器里登录中枢，Casdoor + PKCE）。
- 界面就是现在的工作台网页，跑在应用窗口里，不再开系统浏览器的 `127.0.0.1:17890`。
- 对话、写文案、整理资料这类 agent 任务，由**应用内置的 agent** 完成，模型走中枢的模型网关（按员工计量，额度和审计都在中枢）。
- 知识库、技能、出图、出视频、上报成果，通过**中枢 MCP** 调用（和现在一样，只是由应用自己连，不经过接入器）。
- 有新版本时应用自己从中枢下载更新，下次启动生效。
- 运行出错自动报到中枢「应用健康」页（和现在一样）。

**不做的：**
- 不在员工自己的 Edge 里自动操作，也不用 Playwright；浏览器自动化只发生在应用的内嵌面板里，每一步都经过应用的代码（节奏和额度在那里强制）。
- 不自动发布、不点赞、不评论、不关注、不私信（用户的硬性要求，不变）。
- 第一版不做 macOS（公司电脑是 Windows）。
- 不替代 WorkBuddy：员工想继续在 WorkBuddy 里用中枢的工具（问知识库、出图）照样可以，那条路不变；只是工作台不再依赖它。

## 3. 结构

```
小红书运营工作台.exe（Electron）
├─ 窗口：现有的工作台网页（web/）
├─ 本地服务：现有的工作台 Node 服务（server/），在应用进程里启动，只监听本机
│   ├─ 内容、素材、排期、发布包、图片 / 视频工作流 —— 原样复用
│   ├─ 采集节奏与额度（pace.mjs）—— 原样复用
│   └─ 执行层：换成打包进应用的开源 agent 底座（配中枢的 DeepSeek），替代现在调 CodeBuddy CLI 的 bridge
├─ 登录与令牌：从接入器（hub_agent.py）移植到 Node：PKCE 登录、续期、enroll 领模型 key
├─ 中枢 MCP 客户端：Streamable HTTP + 员工令牌（会话失效自动重连，接入器 0.5.7 的教训）
├─ 浏览器面板（第二阶段）：内嵌浏览器 + 给 agent 的只读浏览器动作（每个动作前过节奏和额度检查）
└─ 更新：问中枢有没有新版本 → 下载 → 校验签名和 SHA-256 → 下次启动换新
```

**能直接复用的**（大部分代码已经有了）：工作台的服务和网页、图片 / 视频 / 中枢出图（`hub-gen.mjs`）、采集节奏与账本、发布包、对标检查点的合并与校验、中枢那一侧的全部接口（登录、enroll、MCP、`/api/v1`、应用健康）。

**要新写的**：
1. 桌面外壳（Electron）：窗口、托盘、单实例、日志。
2. 登录和令牌（移植接入器的逻辑）。
3. **接入 agent 底座**：选型、配置成中枢模型和我们的工具、限制权限，见第 4 节。
4. 安装包、代码签名、自动更新。
5. 中枢一侧：桌面应用的版本发布和下载接口（类似现在的 `apps/` 发布目录，加一个更新清单）。

## 4. agent 底座：用现成的开源 agent，配中枢的模型

现在工作台的对话和任务是交给 CodeBuddy CLI。它的问题不在能力，而在**要单独登录、凭据和 WorkBuddy 共用**。换成一个**开源、能配自定义模型、不需要账号登录**的 agent 底座，打进应用里：

- **模型**：中枢模型网关（New API，OpenAI 兼容）里的 DeepSeek，员工自己的 key（enroll 领取，和现在给 CodeBuddy 写的是同一个）。按人计量、额度和审计都在中枢。
- **工具**：中枢 MCP（知识库、技能、出图、出视频、上报成果）+ 工作台动作（读写笔记 / 素材 / 对标资料、写检查点，背后是现有的服务端函数）+ 浏览器动作（第 5 节）。不给「执行任意命令」。
- **候选底座**（第 0 阶段实测后选一个）：

| 候选 | 好处 | 要验证的 |
|---|---|---|
| OpenCode | 开源；支持自定义 OpenAI 兼容模型和 MCP；有非交互模式和本地服务 / SDK 模式，适合嵌进应用；工作台已有它的适配器 | 官方文档在 Windows 上推荐 WSL，原生 Windows 的稳定性要实测 |
| Qwen Code | 开源，Node 写的（和工作台同一种运行时，Windows 原生）；支持 OpenAI 兼容模型和 MCP | 非交互 / 嵌入方式、工具权限控制 |
| OpenAI Agents SDK（JS） | 是库不是程序，直接在应用进程里跑，Windows 无差别；支持任意 OpenAI 兼容模型和 MCP | 工程化（上下文压缩、重试）比前两个少，要补一些 |

选择标准：在 Windows 上原生能跑、不需要任何账号登录、能把工具限制在我们给的范围、DeepSeek 调工具的成功率达标。

## 5. 浏览器：应用内嵌的浏览器，agent 可以自动操作

不打包 ego lite，不用 Playwright，也不再通过 WorkBuddy 插件操作员工自己的 Edge：

- 应用里有一个**内嵌浏览器面板**（Electron 自带的 Chromium，和 Edge 同一个内核），每个工作台账号一份独立的登录资料。员工第一次在面板里**本人**扫码登录小红书。
- agent 通过应用提供的**浏览器动作**操作它：打开链接、读当前页、滚动、返回、点开主页上的笔记卡片。只读——不给发布、点赞、评论、关注、私信的动作，发布页面直接拦掉。
- 员工能看到 agent 在面板里做什么，也可以随时接手自己操作，或点「停止」。

**这条路比现在好的地方——节奏能真正强制**：现在走 WorkBuddy 插件时，agent 自己决定多快打开下一篇，工作台只能事后看检查点时间。内嵌后**每一个浏览器动作都经过应用的代码**，所以：

- 两次打开页面之间的最小间隔、每天的笔记 / 主页上限、允许时段、冷静期、总开关，**在动作执行前检查，不满足就不执行**（现有的 `pace.mjs` 规则直接用上）。
- 每一个动作都记账（时间、页面类型、去掉参数的链接），出事能复盘。
- 遇到验证码、「操作频繁」、账号异常提示，应用识别到就**立刻停止所有自动操作**并上锁，要人处理后才能恢复（现有的访问锁）。

**要清楚的**：
- 这仍然是自动化，**平台能不能识别、会不会再提示，没法保证**。我们能做的是量少、节奏慢、可叫停、可复盘，**不做伪装**（不改浏览器标识、不改指纹、不模拟鼠标轨迹）。
- 先在测试小红书号上跑；品牌号在冷静期（到 11-02），之后由你决定。
- 内嵌浏览器里登录小红书算一台新设备，可能碰到「设备登录超限」，要在手机 App 里退掉一台旧设备。

## 6. 安装、签名与更新

- **安装包**：electron-builder 打 NSIS 安装包，按用户安装，预计 150MB 左右（含 Chromium 和 Node）。
- **代码签名：不买**。影响：
  - 第一次从浏览器下载安装包时，Windows 多半弹「Windows 已保护你的电脑」，要点「更多信息 → 仍要运行」。装机清单里写清楚这一步。
  - 少数杀软可能把没签名的程序隔离，遇到就加白名单。装机时用 `hub-check` 一类的自检提前发现。
  - **之后的自动更新由应用自己下载**，下载的文件不带浏览器加的「来自互联网」标记，通常不会再弹这个提示（第 1 阶段实测确认）。
  - 校验仍然做：更新包用中枢给的 SHA-256 校验，不对就不装。
- **更新**：应用定期问中枢「最新版本是多少」（类似这次给接入器加的 `agent_version`），有新版就下载安装包，校验 SHA-256，下次启动时安装。中枢加一个发布目录和更新清单。
- **数据**：继续用 `%USERPROFILE%\XHS-Workbench`，现有员工的数据直接沿用，不用迁移；访问锁和采集策略继续放 agent 碰不到的状态目录。

## 7. 分阶段

| 阶段 | 做什么 | 验收 | 量级 |
|---|---|---|---|
| **0. 选底座（先做）** | 2～3 个候选底座 × DeepSeek，在 Windows 上原生跑 3 个典型任务：按知识库写一篇笔记、按要求出 1 张封面并套用、把一份对标资料整理成报告；再加一个浏览器动作的最小样例（在内嵌面板里打开一个测试页并读出标题） | 选出一个底座：每个任务 10 次里成功 ≥8 次、不需要账号登录、工具限制得住；记录耗时和额度消耗 | 约 1 周 |
| **1. 应用第一版** | 桌面外壳、登录、agent 底座、中枢 MCP、出图出视频、发布包、应用健康、安装包和自动更新。**不含小红书页面读取** | 3～5 个员工试用一周：装机 ≤10 分钟、不需要 WorkBuddy / CodeBuddy、「应用健康」里没有新的装机类错误 | 约 2～3 周 |
| **2. 浏览器面板** | 内嵌浏览器 + agent 的浏览器动作（只读），每个动作前过节奏和额度检查，记账，遇风控自动停 | 先在测试号上跑一周：读到的数据和人工看的一致、节奏和上限确实挡得住、没有平台提示；再由你决定是否用于品牌号 | 约 1～2 周 |
| **3. 收尾** | 所有员工换到应用；工作台里的 CodeBuddy / WorkBuddy 插件执行路径保留一段时间再下线；接入器只给想在 WorkBuddy 里用中枢工具的人 | 旧路径没人用了 | 视推广节奏 |

量级是按「一个人专职 + 我这边开发」估的，不是承诺；第 0 阶段的结果会改变后面的估计。

## 8. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| DeepSeek 在所选底座上调工具的成功率不够 | agent 做不好 | 第 0 阶段先实测；底座和工具描述都可以调；实在不够再讨论换模型 |
| 没有代码签名 | 首次安装弹 SmartScreen、少数杀软误报 | 装机清单写清「更多信息 → 仍要运行」；自检发现隔离就加白名单 |
| 依赖开源底座 | 底座升级可能改行为 | 锁定版本、随应用一起打包，升级前跑第 0 阶段的任务集回归 |
| 浏览器自动化被平台识别 | 账号被提示 / 限制 | 节奏和额度由代码强制、先用测试号、遇风控自动停、不做伪装；**风险不能消除** |
| 内嵌浏览器登录算新设备 | 碰到设备上限 | 先在手机 App 退旧设备；或用备选的扩展方案 |
| Electron 包体大（约 150MB） | 首次下载慢 | 局域网从中枢下载，影响不大 |
| 新旧两套并存一段时间 | 维护两条路 | 第 3 阶段定时间表下线旧路径 |
