# GPU 能力节点：部署方案对比

> **当前选择（2026-10-17）**：开发环境采用下文 B1（Windows 同机开发），不是跨网 frp 模式。具体步骤见 [Windows开发交接.md](Windows开发交接.md)；其他方案保留用于未来生产部署评估。

## 背景

现在有两台机器：**中枢**（台式机，Docker 跑全部服务）和 **GPU 机**（Windows + RTX 5080 16GB，跑 ComfyUI）。最初用 Tailscale 把两台机器连起来，多了一个第三方账号、一个常驻进程和一个额外故障点。

关键前提：**代码侧不关心 ComfyUI 跑在哪里**——它只认一个 HTTP 地址，就是 `.env` 里 `HUB_GPU_NODES` 的那一行。所以换任何方案都不改代码，改配置后 `make up` 即可。

`.env` 里那一行长这样：

```
HUB_GPU_NODES=gpu-01|GPU-01 工作站|http://<ComfyUI 地址>:8188|RTX 5080 16GB
```

下面四个方案，按「配置复杂度」从低到高排。

## 方案 A · 局域网直连（零新增组件）★ 首选

**条件**：中枢和 GPU 机在同一个路由器/交换机下（同网段，或路由可达）。

**做法**：
1. Windows 上 ComfyUI 照常启动，参数带 `--listen 0.0.0.0 --port 8188`（已经是这样）
2. Windows 防火墙：8188 入站只放行**中枢机器的 IP**
3. GPU 机设固定 IP（或在路由器里做 DHCP 保留）
4. 中枢 `.env`：`HUB_GPU_NODES=gpu-01|GPU-01 工作站|http://192.168.x.x:8188|RTX 5080 16GB`，`make up`

**优点**：什么都不用装。没有第三方账号、没有隧道进程、没有额外故障点，IP 填完就完事。

**注意**：一定要固定 IP——否则机器重启后地址变了，配置要跟着改。

> 若两台机器本来就在同一个局域网，那 Tailscale 是多余的（当初任务书里写 Tailscale 是「不在一起时的备选」，被当成必做项了）。

## 方案 B · 一台机器全包（中枢与 GPU 合并）

**变体 B1：把中枢搬到 GPU 那台机器上**
Windows 装 Docker Desktop（WSL2 后端），hub 的全部服务跑在里面；ComfyUI 原生跑在 Windows 上；容器通过 `host.docker.internal:8188` 访问本机的 ComfyUI（compose 已配好这条映射，不用额外设置）。
- 优点：**一台机器，零网络配置**
- 缺点：Windows + Docker Desktop 更适合开发与试点；正式交付给 50 人企业用，Linux 更稳（WSL2 内存开销、开机自启、备份都更麻烦）

**变体 B2：把显卡装进中枢服务器**（最干净）
给中枢台式机加一块能放下的 N 卡（或直接把这块 5080 移过去），装 Ubuntu + 驱动 + ComfyUI，与中枢同机；容器访问宿主机端口同样用 `host.docker.internal`。
- 优点：一台 Linux 机器搞定全部，最稳、最好备份、最像正式产品；没有 Windows 那一层
- 缺点：需要硬件条件——电源功率够、PCIe 插槽空着、机箱放得下（5080 是大卡）

## 方案 C · 云 GPU 实例

租一台带 GPU 的云主机（阿里云 / 腾讯云 / AutoDL 等），在上面部署同一套 ComfyUI（用同一份 `gpu-node/workflows/` 模板），中枢通过公网 IP 连；云主机安全组**只放行中枢的出网 IP**。

- 优点：不维护自有机器、不需要打洞、随时能换规格
- 缺点：按小时计费（常驻一张 4090 级别显卡，每月数千元）；首次要上传几十 GB 模型；数据出内网
- 变体：用时才开机——省钱，但员工「一句话出图」要等几分钟机器启动，体验差，不推荐

## 方案 D · 不自己跑模型，改用托管 API

把生图/生视频从「自建 ComfyUI」换成调第三方推理 API（硅基流动 / Replicate / fal.ai 等）。

- 优点：配置最简单（一个 key），零运维，按次付费
- 缺点：**数据出内网**，企业客户通常不接受；失去「私有化」这个产品前提；工作流自由度低
- 注意：这个不是改配置能解决的，要新增一个 provider（把 `gpu.py` 的派发目标从 ComfyUI 换成 API）——**不建议**，除非客户明确只要效果不在乎私有化

## 附：确实跨网络、又不想用 Tailscale 的替代

如果两台机器真的不在一个网络（不同地点），又想避开 Tailscale：

| 方式 | 做法 | 依赖 |
|---|---|---|
| 自建 WireGuard | 中枢服务器上装，Windows 作为客户端连入 | 无第三方，全自己控制 |
| **frp 反向隧道** | 中枢 compose 里起 frps，Windows 跑 frpc 主动外连（**仓库已支持，见 [frp-隧道接入.md](frp-隧道接入.md)**）；中枢填 `http://frps:8189` | 无第三方 |
| Cloudflare Tunnel / ZeroTier | 同类组网工具 | 仍是第三方 |

这三种都是「装一次、之后不用管」，心理负担比 Tailscale 小，但都不如方案 A 干净。

## 安全底线（四个方案通用）

ComfyUI **没有鉴权**，8188 只能在受控范围内可达：局域网内只放行中枢的 IP、云上只放行中枢的出口 IP、走隧道则只有隧道内可见。绝不能直接暴露公网。

## 结论

| 你的情况 | 选 |
|---|---|
| 两台机器在同一个网 | **方案 A**，5 分钟改一行配置 |
| 想要一台机器、能接受 Windows 跑 Docker | 方案 B1 |
| 想要一台机器、能搬显卡 | 方案 B2（最干净） |
| 不想维护自有 GPU 机器、能接受月费 | 方案 C |
| 不在乎数据出内网、只要效果 | 方案 D（需开发） |
| 两台机器确实不在一起、又不用 Tailscale | **frp（仓库已配好）** 或自建 WireGuard |
