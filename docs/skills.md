# 技能库：编辑、版本、审核

技能（`SKILL.md`）存在**数据库**里，带版本，在控制台「技能库」页直接编辑。`skills/` 目录只在首次启动时导入为第 1 版（已有的不覆盖），之后以数据库为准；改磁盘上的文件不会再生效。技能按**部门 id** 归属，部门改名不影响。

## 谁能怎么改

| 角色 | 本部门技能 | 全公司技能 | 其他部门技能 |
|---|---|---|---|
| 部门主管 | 保存即生效 | 提交审核 | 不能改 |
| 老板 / 管理员 | 保存即生效 | 保存即生效 | 保存即生效 |

审核：只有老板和管理员能通过或驳回（驳回要写原因）。一个技能同时只有一份待审核的修改；提交人重新提交会取代自己上一份。

## 版本

- 每次保存都是新版本；**回滚是用旧内容生成新版本**（历史是一条直线，什么都不丢），权限规则同修改。
- 保存时带上基于的版本号，别人先改了就拒绝（409），避免互相覆盖。
- 员工的 agent 读到的永远是「当前生效的版本」：MCP 的 `list_skills` / `read_skill` 和接入器同步（`/api/agent/enroll`）都走 `skillstore.read_skill`；新建后还没通过审核的技能不会被读到，也不会回退到磁盘上的旧文件。
- 内容规则：开头必须有 frontmatter 且含 `name`、`description`，正文不能为空，不超过 64KB。

## 新建技能

主管可以在本部门新建（直接生效）或新建全公司技能（审核）；老板和管理员随意。**新技能要由管理员在「岗位包」里加到对应岗位，员工的 agent 才会用到。**

## 接口（`skills_api.py`，都经过 `auth.console_user`）

| 接口 | 说明 |
|---|---|
| `GET /api/skills/{id}/history` | 版本列表（含内容）、当前这个人能怎么改（`mode`：direct / review / null）、能否审核 |
| `PUT /api/skills/{id}` | 保存（`content`、`note`、`base_version`） |
| `POST /api/skills` | 新建（`id`、`dept`、`content`） |
| `POST /api/skills/{id}/rollback` | 回滚到某个已发布的版本 |
| `GET /api/skill-reviews` | 待审核列表（老板 / 管理员看全部，主管看自己提交的） |
| `POST /api/skill-reviews/{id}/{version}` | 通过 / 驳回（老板 / 管理员） |

每次修改写审计（`skill.edit` / `skill.create` / `skill.rollback` / `skill.review`），只记技能 id、版本和说明，不记内容。

## 技能怎么写：只写业务标准

技能和应用自带的操作手册是**叠加**关系，分工不同：技能（主管 / 老板维护）管**业务标准**——口吻、选题标准、合规红线、回复原则、复盘指标；应用的手册（应用开发维护）管**怎么在应用里做**——文件位置和格式、检查点、受控任务、浏览器与账号安全。技能里**不要写文件格式、存放位置、操作步骤**，否则会和应用手册冲突。每个技能末尾建议写一段「与应用的分工」，写明两者冲突时先停下来说明、并对技能提改进建议。运营部的七个技能就是按这个原则整理的（[草稿记录](drafts/xhs-skills-草稿.md)），小红书运营工作台 0.7.4 起按它叠加使用（见工作台 `docs/hub-integration.md`）。

## 已知限制

- 数据库是唯一真相：想用 Obsidian / git 维护技能的流程不再适用（要改回去需要加「导出到 skills/」）。
- 技能内容里不能有占位的「待补充」之类的内容校验，由负责人把关；没有自动测试技能效果。
- 还没有 agent 提交改进建议的入口（第 4 期）。
