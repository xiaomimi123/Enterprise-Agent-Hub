# 应用分发与「打开工作台」设计

> 状态：待批准 · 2026-10-19（已按独立审查补充第 8 节）
> 关联：[小红书运营工作台](https://github.com/xiaomimi123/-)（独立仓库，Node 本地服务 + 网页）

## 1. 为什么做

公司已有一个独立开发的「小红书运营工作台」：员工在网页里点选题、文案、封面、排期，底层由员工本机的 agent（Claude Code、WorkBuddy 等）操作浏览器和读写本地文件完成。它目前靠「把技能包发给每个人、让 agent 自己装」的方式分发，有三个问题：

1. **分发不可控**：版本散落在每个人手里，更新要逐个通知；谁装了、谁在用，公司不知道。
2. **工作台里的 agent 是孤岛**：它用不了公司知识库、岗位技能和 GPU 出图出视频，权限、额度、审计也都管不到它。
3. **没有统一入口**：员工要记得「把技能包放进 skills 目录再说打开工作台」。

目标：**工作台程序放在中枢上统一发布，员工对自己的 agent 说一句「打开小红书工作台」，工作台就在他本机启动，并且里面的底层 agent 已经接上中枢。**

## 2. 目标、非目标、反目标

**目标**

- 员工对任何已接入中枢的 agent 说「打开小红书工作台」，几十秒内在本机浏览器看到工作台
- 工作台程序由管理员在中枢统一发布和更新，员工端自动拿到新版并校验完整性
- 谁能打开哪个应用由岗位包控制；每次打开写入审计
- 工作台里的底层 agent 自动获得 `enterprise-hub` MCP：公司知识库、岗位技能、GPU 生成，权限与计量沿用现有机制
- 设计成通用的「应用」机制：以后分发第二个、第三个工具不用改代码，只需发布一个新的应用包

**非目标**

- 不把工作台跑在中枢服务器上（它依赖员工本机的浏览器登录状态和本地文件）
- 不改变工作台的业务逻辑和界面；它是独立仓库，由它的作者维护
- 不做托盘图标、桌面快捷方式、双击安装包（触发方式已定为「对 agent 说一句话」）
- 不替员工安装 Node.js（只检查并给出明确指引）
- 本阶段不做应用商店式的自助申请与审批流程

**反目标（出现就算失败）**

- 员工电脑执行了**未经中枢发布、未经校验**的代码
- 没有权限的岗位也能打开应用，或打开了没有审计记录
- 打开失败时 agent 只看到一句「失败」，员工不知道缺什么、怎么办
- 关掉 agent 后，工作台里正在跑的定时发布被意外终止，或反过来，agent 重启后工作台被重复拉起多份

## 3. 已决定的事（来自与你的讨论）

| 决定 | 内容 |
|---|---|
| 触发方式 | 对 agent 说「打开小红书工作台」，由 MCP 工具完成；不做图标或托盘 |
| 分发位置 | 程序放在中枢上，员工通过 MCP 连中枢后取得 |
| 工作台形态 | 员工在网页界面里操作；agent 是底层执行者（浏览器调用等） |
| 底层 agent | 沿用员工自己的 agent；不换成中枢的模型 |

## 4. 我的设计决定（请审阅，不对请指出）

### 4.1 总体流程

```
员工对 agent 说「打开小红书工作台」
  → agent 调用 MCP 工具 open_app(app_id="xhs-workbench")
  → 本机接入器的 MCP 桥拦截这个调用，先转发给中枢：
      中枢校验岗位包是否允许 → 写审计 → 返回「启动凭证」（版本、SHA-256、带签名的下载链接）
  → 桥在本机：检查 Node ≥ 18 → 下载并校验 → 安全解压 → 生成 MCP 配置 → 启动工作台 → 取回网址
  → 桥把结果（网址、连接模式、下一步）返回给 agent，agent 告诉员工「已打开」
```

**为什么由桥执行而不是中枢**：启动本机进程只能在本机做；权限和审计留在中枢，保证与其他工具一致，也保证没有走桥的客户端（直连 MCP）拿到的是「需要本机接入器」的明确提示而不是静默失败。

### 4.2 应用包的发布（中枢侧）

- 目录 `apps/<应用 id>/`，内含 `app.json` 和 `<版本>.zip`。`app.json`：`id`、`name`、`version`、`description`、`entry`（包内启动脚本）、`requires`（如 `{"node": ">=18"}`）、`start_args`。
- 中枢启动时扫描，SHA-256 在加载时计算，不信任文件名。同一应用多个版本时取 `app.json` 声明的版本。
- 下载走签名链接 `/api/apps/<id>/<版本>.zip?exp=…&sig=…`（复用现有 HMAC 签名与常数时间校验，有效期 10 分钟）。
- 本阶段发布方式 = 管理员把 zip 和 `app.json` 放进 `apps/` 目录（与技能库 `skills/`、知识库 `vault/` 一致，只读挂载进容器）；控制台提供「应用」页只读展示（应用、版本、哈希、哪些岗位包可打开、近期打开次数）。上传界面留作后续。

### 4.3 权限

- 岗位包新增字段 `apps`（应用 id 列表，默认空）。`open_app` 要求应用在岗位包的 `apps` 里，且入口为官方 agent（外部智能体一律拒绝）。
- 岗位包编辑页增加「可打开的应用」多选；演示数据里把「小红书运营」岗位包放行 `xhs-workbench`。
- 拒绝返回明确原因（「岗位包『财务』没有打开『小红书运营工作台』的权限」），并记拦截审计。

### 4.4 启动凭证与本机启动

凭证内容：`app_id`、`version`、`sha256`、`download_url`、`entry`、`requires`、`start_args`。桥的本机步骤：

1. **检查 Node**：`node -v` 满足 `requires`；不满足返回按系统给出的安装指引（macOS 用 Homebrew 或官网 .pkg；Windows 用 winget 或官网 .msi），**不自动安装**。
2. **缓存**：包解压在 `~/.hub-agent/apps/<id>/<版本>/`；已存在且 SHA-256 记录一致则跳过下载。保留最近 2 个版本，其余清理。
3. **下载与校验**：下载到临时文件，校验 SHA-256 与凭证一致才解压；不一致丢弃并报错。工作台包只有约 0.8MB、零第三方依赖，不需要 `npm install`，整个流程是秒级。
4. **安全解压**：拒绝绝对路径、`..` 路径、符号链接条目（防 zip slip）；限制解压后总大小（默认 50MB）与文件数（默认 2000）。
5. **生成 MCP 配置**：见 4.5。
6. **启动**：以应用声明的命令在应用目录下运行（工作台为 `node scripts/workbench.mjs setup` 然后 `start --open`），环境变量带上 `HUB_MCP_SERVERS_FILE`、`HUB_TRACE_ID`。工作台的 `start` 本身是幂等的（已在运行时打印「工作台已在运行」并给出同一个 `URL:`），桥直接调用即可。
7. **取回网址**：解析启动命令输出的 `URL:`（该输出契约已在工作台代码中确认）；超时 90 秒报错并附日志路径。

**生命周期**：工作台是常驻本地服务（定时发布、定时检查评论依赖它保持运行），**桥不管理它的生命周期**：agent 退出不会停止工作台；再次说「打开工作台」只是返回网址并确保它在运行；停止由工作台自己的 `stop` 命令（员工对 agent 说「关闭小红书工作台」，由工作台技能处理）。

### 4.5 工作台里的底层 agent 如何接上中枢（跨仓库契约）

工作台已有机制：为 Claude Code 生成 `config/mcp/<账号>.json`（目前只含 Playwright），并以 `--mcp-config` 传入。契约：

- 桥在启动工作台前写 `~/.hub-agent/hub-mcp.json`，内容 `{"mcpServers": {"enterprise-hub": {…}}}`，其中的命令就是员工现在用的 MCP 桥（含令牌自动续期、心跳、技能同步）。
- 桥启动工作台时设置环境变量 `HUB_MCP_SERVERS_FILE=<该文件路径>`。
- **工作台侧需要一处小改动**（在它自己的仓库，`server/browser.mjs` 的 `mcpConfigFor`）：若该环境变量指向的文件存在，把其中 `mcpServers` 的条目并入生成的配置。其他 agent（Codex 等）按各自方式接入，不在本阶段范围。
- 这处改动由工作台作者决定是否接受；中枢侧在没有该改动时照常工作（工作台只是没有中枢能力），不会失败。

### 4.6 审计

- `open_app`：中枢侧写一条「应用」类审计——谁、哪个应用、版本、通过 / 拒绝及原因，与会话共用追踪 ID。
- 桥启动后调用新增接口 `POST /api/agent/app-event` 回报结果（成功 + 网址 / 失败 + 原因，如「缺少 Node」「校验失败」「启动超时」），中枢写第二条审计，控制台审计日志里能看到完整过程。

## 8. 独立审查后补充的结论

一位没看过本次讨论的审查者读了本文档，提出 8 个问题。处理如下：

**已由工作台仓库 / 现有代码回答（写入文档，不再是问题）**

| 问题 | 结论 |
|---|---|
| 包里要不要装 Node 依赖？ | 不要。工作台只用 Node 内置模块，包约 0.8MB / 80 个文件；可选的 Playwright 由工作台自己的 `browser-setup` 装到数据目录，不在包里。上面的大小与时间预算已按此调整 |
| 升级会不会丢员工数据？ | 不会。数据在 `~/XHS-Workbench`（`XHS_WORKSPACE`），在包目录之外；账号、排期、浏览器登录资料都不受版本目录清理影响 |
| 工作台的命令行契约是否真实？ | 真实：`setup`、`start --open`（幂等，输出 `URL:`）、`status`（含「进行中任务 N」）、`stop`；包由其仓库的 `node tools/package.mjs` 生成 `dist/xhs-workbench-v<版本>.zip`，文件名纯 ASCII，可直接作为 `apps/` 里的发布物 |

**我的决定（请审阅）**

1. **升级时正在运行的工作台：绝不自动重启。** 返回现有网址，并附一句「有新版本 vX，关闭工作台后再打开即可升级」。理由：定时发布、定时抓评论都在它进程里，重启会打断；`status` 虽能看到「进行中任务数」，但即使空闲也可能刚好临近定点发布。验收 3 因此改为「**下次启动**时拿到新版」。
2. **Hermes 路径**：Hermes 直连 MCP，不经过桥，拦截点不存在。做法：接入器新增子命令 `hub_agent.py open-app <应用 id>`，与桥共用同一份启动代码；`open_app` 作为**真实工具注册在中枢 MCP 上**（所有客户端都能在工具列表里看到），非桥客户端调用时返回「请在终端运行 `hub_agent.py open-app xhs-workbench`」。Hermes 的深度集成不在本阶段。
3. **嵌套的桥（工作台里的 Claude Code 再启动一个桥）要用精简模式**：通过环境变量 `HUB_BRIDGE_NESTED=1` 跳过技能同步、心跳、`enroll`（不重写技能目录、不覆盖 key、不制造「在线 agent」重复项），并沿用 `HUB_TRACE_ID`，让工作台里发起的中枢调用与 `open_app` 落在同一条链路里。GPU 额度与并发限制按人计，不受影响。
4. **更新发布无需重启中枢**：`open_app` 每次请求按「文件修改时间 + 大小」缓存键判断是否重算 SHA-256；管理员替换 zip 即生效，写进管理员说明。
5. **工作台技能由工作台作者提供**（它的 `SKILL.md` 就在包里）：`open_app` 的返回里给出包内 `SKILL.md` 的路径和「收件箱模式下进入值守」的提示；我们不在中枢侧另写一份。需要时我们只在 `hub-guide` 里加一行「说『打开小红书工作台』就调用 open_app」。

## 5. 交给实现者决定

- 控制台「应用」页的具体版式；`app.json` 的校验细节；日志文件命名与保留策略
- 下载与解压的实现细节（只要满足 4.4 的安全约束）
- macOS 与 Windows 上启动子进程、脱离会话的具体做法（只要满足「agent 退出不影响工作台」）
- 单元测试的划分

## 6. 约束与已知限制

- 目前所有传输走局域网 HTTP，SHA-256 与下载链接来自同一条（已鉴权但未加密的）通道，**不能防止同网段的中间人篡改**；对外使用前必须上 HTTPS，或对应用包做离线签名（后续项）。
- 员工本机需要 Node ≥ 18；没有则无法打开，只能按提示自行安装后重试。
- 工作台的「收件箱模式」要求员工的 agent 会话保持打开并进入值守；`open_app` 的返回里会附上技能路径和「进入值守」的下一步提示，但不替 agent 执行。
- 工作台作者未接受 4.5 的小改动前，工作台里的底层 agent 不会自动获得中枢能力。
- 本机接入器目前无自动更新；应用包更新由「下次打开时对比版本」完成，接入器本身仍需员工重新运行一键接入命令。

## 7. 验收

1. 对已接入中枢的 agent 说「打开小红书工作台」，在本机 Mac 与 Windows 各成功一次，浏览器出现工作台
2. 岗位包不含该应用的员工得到明确的拒绝提示，审计里有拦截记录
3. 管理员替换 `apps/` 里的版本后，员工**下次启动**时自动拿到新版（正在运行的实例不被重启，只收到升级提示）；包被篡改（哈希不一致）时拒绝启动并报错
4. 构造含 `../` 的恶意 zip，解压被拒绝
5. 本机没有 Node 时，agent 收到按系统给出的安装指引
6. 重复说「打开工作台」不会启动多份；agent 退出后工作台仍在运行
7. 审计日志里能看到「打开应用」与「启动成功 / 失败」两条同一追踪 ID 的记录
