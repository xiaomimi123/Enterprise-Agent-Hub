# 控制台「模型」页：接入对话模型与第三方出图 API（设计）

日期：2026-10-19　状态：待确认

## 1. 为什么做

接入一个模型现在要去 New API 后台手动建渠道，那个页面功能太多、太乱，而中枢管理员只需要「把 DeepSeek、中转平台的 key 接进来，让员工的 agent 用上」。同时，中枢出图只有本机 ComfyUI 一条线，并发大了本机会被压垮、效果也下降，需要能切到第三方出图 API。

## 2. 目标

1. 控制台新增「模型」页，管理员不打开 New API 就能：添加 / 停用 / 删除对话模型上游，选择开放哪些模型。
2. 开放的模型出现在岗位包「可用模型」候选里；员工 agent 的调用走这个上游，用量、费用、追踪 ID 沿用现有记录。
3. 同一页面管理「出图通道」：添加第三方出图 API（首个对接 apimart），并用一个总开关在「本机 GPU」与「第三方 API」之间手动切换。
4. 员工与 agent 侧零变化：`generate_image` / `generate_cover` 等工具、每人最多 3 个未完成任务、审计、追踪 ID 照旧。

## 3. 非目标 / 反目标

- 不重做 New API 的计费：不在页面里调模型价格（先用 New API 当前的默认行为）。
- 不做视频的第三方 API；不做按张出图费用折算（只记录出图次数与通道）。
- 不做自动溢出 / 按负载调度（用户选择手动开关）。
- 反目标：密钥不能出现在页面回显、日志、审计详情、错误信息里；管理员以外的人不能看到或改动这页。

## 4. 对话模型上游

**数据在哪：** 上游（渠道）以 New API 为唯一真相，中枢不另存一份；密钥只存在 New API 里。中枢通过已有的 `NewApi` 管理客户端读写渠道。

**页面能力：** 列表（名称、地址、开放的模型、状态、最近测试结果）；添加（名称、地址 `https://xxx/v1`、密钥）；「测试连接」拉取该上游的模型清单（OpenAI 兼容 `GET {地址}/models`，经 New API 的 fetch_models 或中枢直连均可，由实现者按稳定性选）；勾选开放的模型；启用 / 停用；删除；编辑时密钥留空表示不改。

**接口（均需管理员）：** `GET /api/models/upstreams`、`POST /api/models/upstreams/probe`（只探测、不保存）、`POST /api/models/upstreams`、`PATCH /api/models/upstreams/{id}`、`DELETE /api/models/upstreams/{id}`。列表只返回密钥后四位。

**与岗位包的衔接：** 现有 `NewApi.available_models()` 已经只取启用渠道的模型，岗位包「可用模型」的候选改用它；`plan_key` 的交集逻辑不变，所以停用 / 删除上游后，员工的 key 在下次领取配置时自动不再包含这些模型。目录接口 `catalog()` 的 `models` 需要返回真实模型（演示模式保留原样）。

**已知风险（实现者必须先用真实 New API 验证）：** New API 可能拒绝没有配置价格倍率的模型；渠道的创建 / 更新字段以当前部署版本的实际接口为准，不要照着文档猜。

## 5. 出图通道

**配置（存中枢数据库，新表 `hub_settings`，键值 JSON）：**
- `image.route`：`"gpu"`（默认）或 `"api"`，即总开关。
- `image.providers`：出图 API 列表，每项含 id、名称、类型（首个 `apimart`）、地址、模型名、密钥（加密后存放）、是否启用。同一时刻只有被选中的一个生效。

密钥加密：用从中枢已有的服务端密钥（如 `HUB_FILE_SECRET`）派生的对称密钥加密落库；页面只回显后四位；探测 / 保存失败的错误信息不得带出密钥。

**apimart 调用方式（异步）：** 向 `{地址}/v1/images/generations` 提交，响应里取任务号；之后每隔数秒 `GET {地址}/v1/tasks/{任务号}` 查询，状态完成时取图片地址，失败则报错。依据 apimart 的公开博客示例，**具体字段和状态名实现时必须用真实调用核对**，并写进代码注释与文档。

**接入现有流水线（核心取舍）：** API 出图复用现有 `gpu_tasks` 表和 worker，不另起一套：
- `submit_image` / `submit_cover` 在提交时读取 `image.route`；为 `api` 时任务的 workflow 记为 `api-image`，其余参数、每人 3 个未完成任务的限制、审计、追踪 ID、`get_task` 的描述与下载链接都不变。
- `claim_task_for(node)` 不得把 `api-image` 任务派给 GPU 节点；worker 里新增 API 分支：领取排队中的 `api-image` 任务（同时进行的上限可配置，默认 4），提交到出图 API，把第三方任务号存进 `prompt_id`，每轮轮询结果。
- 完成后把图片**下载到 `HUB_OUTPUTS_DIR` 本地**，员工拿到的仍是中枢签发的链接，不依赖第三方链接的有效期。
- 超时、失败的处理沿用现有的重试一次与审计；API 任务不占 GPU 并发、不显示在 GPU 节点占用里；「生成任务」页的任务带上「通道」（本机 GPU / 第三方 API）。
- 切换开关只影响**之后**提交的任务；已在排队或运行的任务按提交时的通道完成。
- 提交到出图 API 之前先把第三方任务号落库（重启 worker 后恢复轮询、不重复出钱）。
- `generate_cover` 一次 3 版：API 通道下提交 3 次或按接口的张数参数，由实现者按接口实际能力决定，但对员工仍是一次返回 3 张。

**页面能力：** 出图通道卡片显示当前通道；总开关；添加 / 编辑 / 删除出图 API；「测试」用一张最小尺寸图实际跑一次并显示耗时与结果（测试不计入员工任务、不进「生成任务」页）。当通道为 `api` 但没有可用的出图 API 时，开关不允许切换，页面给出原因。

## 6. 权限与审计

- 「模型」页和相关接口仅管理员；非管理员访问返回 403。
- 每次增删改上游 / 出图 API、切换通道、测试，都写一条审计（操作者、对象名称、结果；不含密钥）。

## 7. 验证标准

1. 真实 New API 上：通过页面接口添加一个上游 → 测试连接拉到模型 → 开放 → 在岗位包勾选 → 员工领取配置后 key 包含该模型 → 用该 key 真实调用一次成功；停用后再领取不再包含。
2. 出图：用 mock 的 apimart 兼容服务做自动化测试（提交、轮询、失败、超时、重启恢复）；并用真实的 apimart key 做一次端到端（该 key 由管理员在页面里填，不写进仓库）。
3. 切换通道后新任务走新通道、旧任务不受影响；`get_task` 与下载链接行为一致。
4. 密钥不出现在任何接口响应、日志、审计里（有测试）。

## 8. 留给实现者的决定

探测模型清单的方式；`hub_settings` 的表结构细节；API 并发上限的配置名；`generate_cover` 在 API 通道下的具体提交方式；页面的具体布局（沿用现有的页面样式与亮 / 暗两套主题）。
