# 2 系统概述

中枢是面向约 50 人企业的**私有化多智能体平台**。它不是又一个聊天机器人，而是员工 AI 助手背后的「控制平面」：统一管理身份、权限、知识、技能、算力、模型和审计，让每个岗位的员工用自己顺手的 agent 干活，同时让公司对数据边界、内容质量和成本心里有数。

## 2.1 设计原则

| 原则 | 含义 | 在代码里的体现 |
|---|---|---|
| 权限在中枢强制执行 | 能看什么、能做什么由服务端判定，与提示词无关；注入「忽略限制」与普通越权同样被拒 | `policy.py` 集中判定员工的 agent 权限；每个 MCP 工具入口先算 `Principal`，再查岗位包 |
| 默认拒绝 | 控制台接口对老板和主管只开放白名单；新增接口默认只有管理员能用，忘记配置也不会泄露 | `auth.console_user` + `ROLE_ALLOWED` 白名单；管理接口显式要求管理员 |
| 管 agent，不管人 | 管理员看到的是 agent 的调用链路、用量和拦截，而不是员工屏幕 | 审计按调用落库（`audit_events`），控制台按追踪 ID 聚合成链路 |
| agent 只提建议，人来决定 | agent 发现技能或知识库有问题时只能提交建议，采纳由主管或老板审核，采纳后才产生新版本 | `proposals.py`；采纳走 `skillstore` / `kbstore` 的版本流程，可回滚 |
| 数据库是内容的唯一真相 | 技能和知识库文档在控制台编辑，每次保存都是新版本；磁盘目录只在首次启动时导入 | `skills` / `skill_versions`、`kb_docs` / `kb_doc_versions` |
| agent 不绑定 | 员工可以用 Hermes，也可以用 WorkBuddy、CodeBuddy CLI、Cursor、Claude 桌面版；中枢只管经过中枢的资源 | 标准 MCP 接口 + 本地 stdio 桥；计费按「中枢资源」与「模型 token」分开 |
| 开源组件优先，薄胶水层 | 身份、模型网关、知识检索、生图都用成熟开源组件，自研只做权限、治理、调度、计量与集成 | Casdoor / New API / RAGFlow / ComfyUI |
| 故障降级而非中断 | 知识库、GPU 节点、网络、中枢本身任一出问题，主流程尽量继续 | RAGFlow 失败回退本地检索；GPU 掉线自动改派；桥接出错返回 JSON-RPC 错误不退出；应用读不到中枢能力时只禁用对应功能 |
| 先说清楚再动手 | 依赖缺失、权限不足、内容冲突时，给出可执行的说明，而不是悄悄失败或擅自选择 | 能力预检的「缺什么、怎么装」；过期建议要确认；中枢技能与应用手册冲突时 agent 先停下来说明 |

## 2.2 功能全景

| 能力域 | 已实现功能 |
|---|---|
| 身份与组织 | Casdoor 统一登录（自建账号，不接钉钉）；三类应用区分入口；部门即 Casdoor 分组，可在控制台新建、改名、删除；部门默认岗位包；按人改派 |
| 控制台角色 | 管理员 / 老板 / 部门主管；老板看全公司，主管只看和管自己的部门；接口默认拒绝；部门与角色页 |
| 技能库 | 控制台在线编辑、新建、版本历史与差异、回滚；本部门保存即生效，全公司技能由主管修改需老板或管理员审核；按岗位包下发到各类 agent |
| 知识库 | 文档在线查看、新建、编辑、删除（可找回）、版本与回滚；内容类型、负责人、复核周期、逾期提示；发布后同步到 RAGFlow 混合检索；按岗位包与密级过滤 |
| 改进建议 | agent 通过 MCP 提交技能 / 知识库的修改建议，主管或老板审核后采纳、修改后采纳或驳回，原因反馈给提出人 |
| 工作成果 | agent 或应用上报「做成了什么」，控制台工作看板按岗位和个人展示；老板的 agent 可定时拉日报 |
| GPU 生成 | 文生图、文生视频、图生视频；本机 GPU、第三方 API、H3 网关三条线，通道手动切换；PostgreSQL 任务队列；容错改派 |
| 模型网关 | New API；员工专属 key；按岗位包限制模型与月额度；按模型设置价格；按人计量 |
| 员工端 | 一条命令接入；自动配置 WorkBuddy / CodeBuddy CLI / Cursor / Claude；令牌自动续期；技能同步；在线上报 |
| 应用分发 | `open_app` 下载、校验、启动本机应用；`app.json` 声明依赖，打开前预检并询问安装；应用成果经本机 outbox 转发到中枢 |
| 审计与计量 | 全链路追踪 ID；中枢资源计量；GPU 额度与并发限流；拦截与配置变更留痕 |
| 控制台 | 总览、成员与组织、部门与角色、岗位包、技能库、知识库、改进建议、模型、应用、接入方式、工作看板、审计、生成任务、用量；亮 / 暗双主题；菜单按角色显示 |

## 2.3 术语表

| 术语 | 说明 |
|---|---|
| MCP | Model Context Protocol，agent 调用外部工具的开放协议；中枢以 Streamable HTTP 方式提供 MCP Server |
| Principal | 一次调用背后的主体：组织、用户、部门、入口（官方 / 外部）、是否管理员和解析后的岗位包 |
| 追踪 ID（trace_id） | 一次工作会话的标识；同一任务的登录、检索、生成、模型调用共用它 |
| 控制台角色 | 管理员（Casdoor 的 `isAdmin`）、老板、部门主管；老板和主管的名单存在 `console_roles` |
| 版本 / 已生效版本 | 技能和知识库文档的每次保存都是新版本；员工的 agent 读到的永远是「已生效版本」 |
| 直接生效 / 提交审核 | 同一次保存，按角色和内容归属，要么立即生效，要么进入待审核（5 节之后的各章详述） |
| 改进建议 | agent 提交的、尚未生效的修改意见，审核后才可能变成新版本 |
| 应用 / 应用手册 | 通过中枢分发到员工本机的程序（如小红书运营工作台）/ 应用自己的操作手册，与中枢技能叠加使用 |
| 能力预检 | 打开应用前检查 `app.json` 声明的依赖，缺什么说明并询问安装，只让对应功能不可用 |
| outbox | 应用把关键产出追加写入的本机文件，接入器转发到中枢 |
| GPU 节点 | 一台运行 ComfyUI 的机器，在 `HUB_GPU_NODES` 中登记 |
| MCP 桥 | 接入器的 `mcp` 子命令：stdio ↔ Streamable HTTP 转发，并负责令牌续期、心跳和成果转发 |
| 中枢资源 | 经过中枢的可计量资源：工具调用、GPU 用时、出图张数、视频条数 |
