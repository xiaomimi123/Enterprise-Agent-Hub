# 6 技能库与版本治理

技能是一份 Markdown（`SKILL.md`，开头带 `name`、`description` 的 frontmatter），告诉 agent 某类工作该怎么做。技能直接指挥全公司员工的 agent，所以它的修改必须**可追溯、可回滚、可审核**。技能库把技能存进数据库，在控制台里编辑，并按角色决定「保存即生效」还是「先审核」。

## 6.1 为什么存数据库

最初技能是仓库里的文件（`skills/<部门>/<技能 id>/SKILL.md`，业务人员用 Obsidian 编辑，提交 git 后下发）。这个流程对业务主管不友好：不会用 git，改错了没法回滚，也没有审核。现在：

- 首次启动时把 `skills/` 目录导入数据库为第 1 版（已有的不覆盖），之后以数据库为准，磁盘文件只是初始数据；
- 技能按**部门 id** 归属（`all` 表示全公司），部门改名不影响它；
- 员工的 agent 通过 `list_skills` / `read_skill`、接入器同步读到的永远是**已生效版本**；新建后还在等审核的技能不会被读到，也不会回退到磁盘上的旧文件。

```sql console/backend/app/db.py — 技能表
CREATE TABLE IF NOT EXISTS skills (
    id                TEXT PRIMARY KEY,
    dept_id           TEXT NOT NULL,             -- 部门（Casdoor 分组名）或 all（全公司）
    name              TEXT NOT NULL DEFAULT '',
    description       TEXT NOT NULL DEFAULT '',
    published_version INTEGER NOT NULL DEFAULT 0, -- 0 = 还没有已发布的版本（新建后等审核）
    ...
);
CREATE TABLE IF NOT EXISTS skill_versions (
    skill_id    TEXT NOT NULL REFERENCES skills(id) ON DELETE CASCADE,
    version     INTEGER NOT NULL,
    content     TEXT NOT NULL,
    author      TEXT NOT NULL DEFAULT '',  author_name TEXT NOT NULL DEFAULT '',
    note        TEXT NOT NULL DEFAULT '',
    status      TEXT NOT NULL,                   -- published | pending | rejected
    reviewer    TEXT NOT NULL DEFAULT '',  review_note TEXT NOT NULL DEFAULT '',
    reviewed_at TIMESTAMPTZ,  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (skill_id, version)
);
```

## 6.2 谁能怎么改

规则只有一张表，由 `plan_for` 实现：

| 角色 | 本部门技能 | 全公司技能 | 其他部门技能 |
|---|---|---|---|
| 部门主管 | 保存即生效 | 提交审核 | 不能改（也看不到） |
| 老板 / 管理员 | 保存即生效 | 保存即生效 | 保存即生效 |

审核只有老板和管理员能做（驳回必须写原因）。一个技能同时只有一份待审核的修改；提交人重新提交会取代自己上一份，别人的待审核修改在审核完成前不能再提。

## 6.3 版本、冲突与回滚

- **每次保存都是新版本**。回滚不是「改回去」，而是**用旧版本的内容生成一个新版本**：历史永远是一条直线，什么都不丢，回滚本身也走同样的权限和审核规则。
- **乐观并发**：保存时带上自己基于的版本号（`base_version`），如果技能已被别人更新，返回 409 并要求在最新内容上重新修改，避免互相覆盖。
- **事务**：`db.connect()` 是自动提交的，涉及多张表或需要行锁的写操作都包在 `_tx()` 事务里；提交用 `SELECT … FOR UPDATE` 锁住技能行。
- **内容校验**（`clean_content`）：必须有 frontmatter 且含 `name` 和 `description`，正文不能为空，不超过 64 KB，统一换行符。

## 6.4 技能怎么写：只写业务标准

技能与应用自带的操作手册是**叠加**关系（ADR-9）。技能（主管 / 老板维护）管**业务标准**：口吻、选题标准、合规红线、回复原则、复盘指标；应用手册（应用开发维护）管**怎么在应用里做**：文件位置和格式、检查点、受控任务、浏览器与账号安全。因此技能里**不要写文件格式、存放位置、操作步骤**，否则会和应用手册冲突。控制台的新建模板和编辑器提示也强调这一点；每个技能末尾建议写一段「与应用的分工」，写明两者冲突时先停下来说明、并对技能提改进建议。

运营部的七个技能（选题、拆解、文案、封面、合规、评论、复盘）就是按这个原则，从小红书运营工作台的手册里提炼业务标准写成的，详见 14 章。

## 6.5 接口与审计

| 接口 | 说明 |
|---|---|
| `GET /api/skills`、`GET /api/skills/{id}` | 列表与详情（主管只看自己部门和全公司） |
| `GET /api/skills/{id}/history` | 版本列表（含内容）、当前这个人能怎么改（`direct` / `review` / 不能）、能否审核 |
| `PUT /api/skills/{id}` | 保存（`content`、`note`、`base_version`） |
| `POST /api/skills` | 新建（`id`、`dept`、`content`）；新技能要由管理员在「岗位包」里加到岗位，员工的 agent 才会用到 |
| `POST /api/skills/{id}/rollback` | 回滚到某个已发布的版本 |
| `GET /api/skill-reviews`、`POST /api/skill-reviews/{id}/{version}` | 待审核列表 / 通过或驳回（老板、管理员） |

每次修改写审计（`skill.edit` / `skill.create` / `skill.rollback` / `skill.review`），只记技能 id、版本和说明，不记内容。
