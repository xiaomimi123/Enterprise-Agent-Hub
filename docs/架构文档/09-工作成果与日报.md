# 9 工作成果与日报

老板要看的不是「调用了多少次工具」，而是各岗位、各成员**做成了什么、进度如何**。原有的审计只记录活动，这一层在它之上补出**成果**：员工的 agent 或应用上报产出，控制台按岗位和个人汇总，老板的 agent 可以定时拉日报。

## 9.1 两类数据，主指标是成果

| 类型 | 来源 | 回答什么 |
|---|---|---|
| **成果**（主指标） | 员工的 agent 调用 `report_work`，或应用经 outbox 自动上报：标题、类型、状态、进度、产物链接 | 做成了什么、卡在哪 |
| **活动**（参考） | 自动统计：审计事件、GPU 任务（出图 / 视频数、调用数、活跃天数、期间无活动的人） | 在不在做 |

调用数和 token 可以被刷，所以不能当绩效；看板的主指标是成果和完成情况。成果只存标题、类型、状态、进度、可公开的链接和一句话说明，**不存提示词和正文**，员工不会觉得被监控。

```sql console/backend/app/db.py — 工作成果表
CREATE TABLE IF NOT EXISTS work_items (
    id BIGSERIAL PRIMARY KEY,
    org TEXT NOT NULL, user_name TEXT NOT NULL, display_name TEXT, dept TEXT,
    kind TEXT NOT NULL DEFAULT '其他', title TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT '已完成',            -- 进行中 | 待审核 | 已完成 | 受阻
    progress INTEGER NOT NULL DEFAULT 100, link TEXT, note TEXT,
    source TEXT, trace_id TEXT, ext_key TEXT NOT NULL DEFAULT '',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(), updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 应用自动上报的幂等键：同一个人、同一来源、同一个 key 只有一条，重复上报是更新
CREATE UNIQUE INDEX work_items_ext ON work_items (org, user_name, source, ext_key) WHERE ext_key <> '';
```

## 9.2 上报：agent 与应用两条路

- **agent 上报**：员工的 agent 完成有交付物的工作（笔记草稿、对标报告、选题表）或状态变化（待审核、受阻）时调用 `report_work`；继续更新同一项带上次返回的 `item_id`，且**只能改自己的条目**。校验：标题必填，状态必须是四种之一，链接只能是 http(s)（不放本机文件路径），字段长度受限。
- **应用自动上报**：应用把关键产出追加写进本机 outbox，接入器转发到 `POST /api/agent/work-report`，中枢按「人 + 应用 + key」幂等写入（`report_batch`，一次最多 50 条，坏条目跳过并说明原因，好的照常写入）。小红书运营工作台目前上报笔记状态变化（草稿 → 待发布 → 已发布）和对标拆解完成，只写标题和状态。机制见 13.4 节。

## 9.3 汇总：build_report

`work.build_report` 是纯函数（不连库，便于测试）：把审计事件、成果、GPU 任务按人汇总，再按岗位汇总，并产出一段事实摘要 `digest` 供 agent 写日报。口径：

- 「今天」从今天 0 点起；N 天含今天往前数 N 个自然日；
- 成果按「最后更新时间」落在区间内计入，同一项更新为已完成后算一项；
- 出图 / 视频只数成功的 GPU 任务；岗位按成员的岗位包（未指派按部门默认岗位包，4.3 节）；
- 控制台传入成员列表时，能识别「期间没有任何活动的人」；
- `depts` 参数让部门主管只看到自己部门。

`load_report` 在此基础上并入两项治理信息：**逾期没有复核的知识库**（7.6 节）和**待处理的改进建议数**（8 章），并追加到 `digest`。

## 9.4 控制台看板与老板的日报

- **工作看板**（控制台「工作看板」页）：今天 / 近 7 天 / 近 30 天；KPI；按岗位 / 按个人切换；成果清单（状态、负责人、产物链接）；没有任何上报时明确提示「需要员工的 agent 调用 `report_work` 或应用接入上报」。主管只看到自己的部门。
- **老板的 agent 每天推送日报**：老板用自己的 agent 连中枢 MCP，让它每天定时调用 `team_report(days, person)`，拿到按岗位 / 成员的汇总、成果清单、受阻项、期间无活动的人、逾期知识库、待处理建议数，以及 `digest` 事实摘要，agent 据此写日报。**定时由老板那个 agent 自己的定时任务触发，中枢不主动推送、也不在服务端调用模型写日报**。
- **权限按控制台角色**：老板和管理员看全公司，部门主管只看自己负责的部门，其他员工和外部智能体不能调用（4.5 节）；范围由服务端按调用者身份算，不取决于参数。

## 9.5 限制

- 成果依赖 agent 或应用上报，没上报的工作看不到；应用的自动上报只覆盖应用里已接好的钩子（agent 绕过应用接口直接改文件的不会上报）。
- 目前没有「目标 / 任务指派」，所以没有完成率；等看板用起来、确定口径后再做。
- 看板里「期间无活动」在控制台列出成员时才完整；`team_report` 只看有记录的人。
