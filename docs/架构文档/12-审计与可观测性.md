# 12 审计与可观测性

「管 agent，不管人」的落点是审计：管理员和老板看到的是 agent 的调用链路、拦截、用量和配置变更，而不是员工屏幕。2.0 版审计覆盖的范围比 1.0 大得多：除了工具调用，**控制台里的每一次配置和内容变更**、应用启动、成果上报、改进建议也都留痕。

## 12.1 审计数据模型

`audit_events` 采用「一步一行」的事件表：每次工具调用、每次拦截、每次生成完成、每次配置变更都是一行，同一任务共用 `trace_id`。控制台把事件按追踪 ID 聚合成「链路」：步骤、总 token、花费、结果（任一步拒绝 → 被拦截；有待确认 → 待审批；否则成功）。

| 字段 | 说明 |
|---|---|
| trace_id | 追踪 ID；接入器每次会话生成 `tr-<12 位>`，经 `X-Hub-Trace-Id` 传递；应用启动的工作台里的 agent 沿用同一个 ID |
| channel | 官方 agent / 外部智能体 / 控制台 |
| kind | 登录 / 检索 / 技能 / 工具 / 生成 / 模型 / 拦截 / 应用 / 配置 / 工作 / 建议 |
| tool | 工具代号：`kb.search`、`skill.read`、`image.generate`、`llm.chat`、`app.open`、`app.launch`、`work.report`、`proposal.create` 等；控制台操作用 `skill.edit`、`kb.edit`、`dept.create`、`role.managers`、`model.pricing.set` 等 |
| result | 通过 / 拒绝 / 待确认 |
| detail / summary | 人能读懂的一句话；summary 为任务描述（来自 `X-Hub-Task`） |
| tokens / model / cost | 模型调用步骤的用量（由 New API 日志并入） |

**配置变更的审计只记「谁改了什么」，不记内容和密钥**：技能和知识库只记 id、版本、说明，成员只记用户名和动作（不含密码），模型和出图 API 的密钥永远不进审计。

## 12.2 模型调用归属：会话专属 key 优先，时间窗兜底

模型网关只认员工 key，看不到追踪 ID，而 New API 也不会记录客户端传来的任何自定义信息（请求头、`user`、`metadata` 均实测，日志里都没有），只记 key 的**名字**。所以 `hub_agent.py chat` 领取配置时请求「会话专属 key」：`hub-<组织>-<用户>~<追踪 ID>`（3 天后过期），调用日志的 `token_name` 直接指明属于哪条链路，**精确归属优先**；基础 key（普通 `sync`、WorkBuddy 桥接）的调用仍按「**同一员工 + 链路时间窗**」兜底：窗口从链路第一步开始，到该员工下一条链路开始为止，最长到最后一步之后 10 分钟（模型在最后一次工具调用后还要组织回答）。只处理官方 agent 入口，因为外部智能体不使用员工的模型 key。

## 12.3 员工端在线状态

两个信号刷新在线时间：接入器 MCP 桥每 60 秒的心跳（带 agent 名称、版本、系统），以及官方 agent 的任意工具调用（覆盖直连 MCP 的 Hermes）。`touch_presence` 使用 upsert，并用 `coalesce` 保留未提供字段的旧值——工具调用只知道「人」，不知道用的是哪个 agent。5 分钟内有信号为「在线」，之前出现过为「离线」，从没出现过为「未安装」。总览的近 14 天趋势来自 `agent_presence_daily`（每人每天一行）和审计里结果为「拒绝」的事件。
