# 13 员工端接入器与应用分发

接入器 `agent/hub_agent.py` 是一个单文件 Python 脚本（uv 内联依赖：httpx、pyyaml），负责把任何 agent 接到中枢，并在员工电脑上下载、校验、启动中枢分发的应用。它**不修改任何 agent 的源码**，只生成配置和提供协议桥接，因此 agent 升级不受影响。

## 13.1 子命令

| 子命令 | 作用 |
|---|---|
| `setup --hub URL` | 一键接入：未登录则浏览器登录 → 同步 → 自动配置本机的 WorkBuddy / CodeBuddy CLI / Cursor / Claude 桌面版 |
| `login --hub URL` | 浏览器登录（PKCE）；开发环境可用 `--username` / `--password` |
| `sync` | 领取配置：模型 key、MCP 地址、岗位包技能；写 Hermes 专用配置、同步 WorkBuddy 技能和 CodeBuddy 模型 |
| `mcp --client NAME [--nested]` | MCP 桥（stdio ↔ Streamable HTTP），由桌面 agent 启动；`--nested` 给应用里的 agent 用 |
| `chat` | 用专用 `HERMES_HOME` 启动 Hermes（先自动同步） |
| `open-app APP` | 在本机打开中枢发布的应用（给不走 MCP 桥的客户端） |
| `app-doctor APP [--yes]` | 重新检查应用的依赖并（经询问）安装缺少的部分 |
| `flush-outbox [APP]` | 立即把应用写在本机的工作成果转发到中枢 |
| `status` / `logout` | 查看状态 / 清除本机令牌、key 和技能 |

一键脚本由中枢动态下发（`/api/agent/install.ps1`、`install.sh`，下发时把中枢地址填进模板）。脚本先检测 Node.js 和 CodeBuddy CLI，**缺什么先说明、询问后才安装**，不会悄悄装东西；Windows 版脚本刻意只用 ASCII 字符，因为 Windows PowerShell 5 通过管道执行脚本时可能按系统代码页解码，非 ASCII 字符会变成乱码。

## 13.2 MCP 桥：stdio ↔ Streamable HTTP

WorkBuddy 等桌面 agent 以「本地命令」方式启动 MCP 服务器，通过 stdin/stdout 逐行交换 JSON-RPC 消息。桥把每条消息 POST 到中枢，并把响应写回 stdout：

- 每次请求前调用 `fresh_creds()`，令牌快过期时自动续期，再带上 `Authorization` 头。
- 首次响应头里的 `mcp-session-id` 被记住并在后续请求回传；中枢重启导致会话失效（404）时，去掉会话号重试一次，实现透明重连。
- 响应为 JSON 时原样转发；为 `text/event-stream` 时按 SSE 规则拆帧：累积 `data:` 行，遇到空行输出一条消息。
- 202（通知的确认）不输出；任何异常都转成一条 JSON-RPC 错误回给客户端，**桥本身不退出**，避免 agent 侧反复重启 MCP 服务器。
- **stdout 只允许输出协议消息**：所有提示信息改写到 stderr，否则会破坏客户端的 JSON 解析。

非嵌套的桥启动时先开两个后台线程：每 60 秒的**心跳**（在线状态，12.3 节）和每 20 秒的**成果转发**（13.7 节），再同步一次岗位包技能；各项失败都只写 stderr，不影响桥本身。嵌套桥（`--nested`，由应用里的 agent 启动）不同步技能、不报心跳，沿用外层的 `HUB_TRACE_ID`，让应用里发起的调用与「打开应用」落在同一条审计链路。

## 13.3 一键接入：安全地修改别人的配置文件

`configure_agents` 要修改第三方 agent 的配置文件，必须满足四个性质：保留原有内容、可回滚、幂等、对异常输入不破坏。实现上：

- 只增改 `mcpServers.enterprise-hub` 一项，其余键原样保留。
- 有改动才写；写之前把原文件备份为 `*.bak-hub-<时间>`；已是最新则不动、不备份（幂等）。
- JSON 解析失败的配置文件**不覆盖**，只报告「格式有误，已跳过」。
- 读取时用 `utf-8-sig` 兼容带 BOM 的文件（Windows 工具常见）；写入固定 UTF-8。
- 配置中写 `uv` 的**绝对路径**：桌面 agent 启动子进程时不一定继承用户的 PATH。

## 13.4 技能同步的所有权模型

WorkBuddy 的技能目录里同时存在员工自己安装的技能和中枢下发的技能。接入器用「**前缀 + 标记文件**」声明所有权：只管理 `hub-` 开头且含 `.hub-managed` 标记的目录。岗位包撤掉的技能被删除；同名前缀但没有标记的目录（员工自建）不受影响。技能正文在 frontmatter 之后插入一行来源说明，frontmatter 必须保持在文件最前面，否则 WorkBuddy 无法识别技能。另生成 `hub-guide` 技能，告诉模型何时调用中枢工具。同步的内容是各技能的**已生效版本**（6 章）。

## 13.5 CodeBuddy CLI 适配

要让应用（如工作台）的底层 agent 自动控制浏览器，需要 CLI 模式的命令行 agent。`setup` 会自动检测 CodeBuddy CLI 并配置：

- 把中枢写进它的 MCP 配置（已有 `mcp.json` 时写那个文件，避免顶掉员工原有的服务器）；
- 把**岗位包允许的中枢模型**写进 `~/.codebuddy/models.json`（条目名带「公司中枢 · 」前缀，`url` 为完整的 `/v1/chat/completions`，`apiKey` 是员工本人的 key，权限 600）；员工没选过默认模型时设为中枢默认模型，员工之后自己改了就不再覆盖；岗位包改成「自带模型」时清掉中枢写入的条目；
- 在 `settings.json` 的 `permissions.allow` 追加 `DeferExecuteTool`：CodeBuddy 把 MCP 工具当延迟加载工具，无人值守（`codebuddy -p`）时没有权限弹窗，不放行就会被拒绝；中枢工具本身仍由岗位包按人限制。

改动前都会备份，格式有误的文件不覆盖。已在真实的 CodeBuddy CLI 2.171.0 上验证。踩过的坑：提示词必须走标准输入（Windows 的 `.cmd` 垫片会在第一个换行处截断命令行参数）；`--allowedTools` 是多值参数，每个工具名要单独一项（逗号拼成一项不生效）。

## 13.6 应用分发：open_app

员工对 agent 说「打开小红书工作台」→ agent 调 `open_app` → 中枢核对岗位包并返回**启动凭证**（带签名下载链接、SHA-256、入口、依赖声明）→ 本机 MCP 桥拦截该返回，在本机完成：

1. 预检依赖（13.7 节）；
2. 下载 zip 并核对 SHA-256（`fetch_verified`），已有同版本同哈希则复用；
3. **安全解压**（`safe_extract`）：拒绝绝对路径、`..`、符号链接，限制解压后总大小（50 MB）和文件数（2000）；
4. 在包目录下执行应用的 `setup`（每次都跑，必须幂等）和 `start`，从输出里取 `URL:` 行；
5. 向中枢回报启动结果（审计 `app.open` + `app.launch` 同一 trace ID，失败带原因，缺失的能力写进详情）。

同一应用并发打开串行化；**运行中的实例绝不重启**（应用里有定时发布、定时检查等任务），新版本只提示「关闭后再打开即可升级」；保留最近 2 个版本。不走 MCP 桥的客户端（如 Hermes）用 `hub_agent.py open-app`。

## 13.7 依赖预检、app-doctor 与成果转发

**依赖预检**：应用在 `app.json` 的 `requires` 里声明依赖（目前 `agent_cli`: `codebuddy`、`capabilities`: `["browser"]`、`playwright_mcp` 版本）。打开前 `preflight` 检查 Node / npx、CodeBuddy CLI、中枢模型（`models.json` 里有中枢下发的模型）、系统浏览器（Edge / Chrome / Chromium）、Playwright。**缺东西时应用照常打开**，只有对应功能（如浏览器自动化）不可用；接入器把「缺什么、怎么装、是否同意安装」附在返回消息里。结果写进 `~/.hub-agent/capabilities/<应用>.json`（不含密钥），并通过环境变量 `HUB_CAPABILITIES_FILE` 交给应用，应用每次使用时重读，装好后无需重启。

**app-doctor**：`app-doctor <应用>` 逐项询问后安装（`--yes` 表示员工已对 agent 同意）。**只有可自动的项**（如 `npm install -g @tencent-ai/codebuddy-code`、同步中枢模型）会被执行，系统浏览器、Node.js 只给手动安装提示，永远不会被自动运行。

**成果转发（outbox）**：接入器启动应用时设置 `HUB_WORK_OUTBOX=~/.hub-agent/outbox/<应用>.jsonl`，应用把关键产出追加写进去（一行一条 JSON，带固定的 `key`）。MCP 桥每 20 秒（或手动 `flush-outbox`）按**字节偏移**读取新内容，只处理完整的行，一次最多 50 条 POST 到 `/api/agent/work-report`：网络错误和 5xx 不推进偏移，下次重试；中枢拒绝的批次（其他 4xx）跳过，不卡住后面的行；文件被清空重写（比偏移短）就从头来。中枢按「人 + 应用 + key」幂等写入，所以两个桥同时在跑、重复转发都只是更新。
