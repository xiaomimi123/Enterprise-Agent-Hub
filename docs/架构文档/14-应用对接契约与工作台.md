# 14 应用对接契约与小红书运营工作台

中枢不只是给 agent 提供工具，它还能把**成熟的开源工作台或智能体**改造成公司的应用：由中枢统一分发、权限控制、审计，应用里的 agent 接入中枢的知识、技能和模型。这套「**应用托管 + 对接契约**」模式的第一个样板是小红书运营工作台（独立仓库，约 130 个文件，零第三方依赖）。完整的接入指南见 `docs/app-integration-guide.md`，本章总结契约和叠加原则。

## 14.1 三个层级

| 层级 | 做什么 | 例子 |
|---|---|---|
| 1 托管 | 中枢分发、校验、启动本机应用，岗位包控制谁能打开 | `open_app`、`app.json`、签名下载 |
| 2 对接 | 应用里的 agent 接入中枢 MCP，应用读取中枢给的依赖预检结果，应用把产出回报给中枢 | 三个环境变量契约（14.2） |
| 3 治理 | 业务标准由中枢技能统一维护，应用手册只管操作；发现问题通过建议反馈 | 技能叠加（14.3）、改进建议 |

应用不必做到第 3 层才有价值；每一层都是可选的、失败时优雅降级的。

## 14.2 环境变量契约

中枢接入器启动应用时设置下面几个环境变量，应用据此对接。**共同原则：没有变量、文件不存在或内容不合法时，应用一切照旧，不报错、不拦任何功能。**

| 环境变量 | 内容 | 应用怎么用 |
|---|---|---|
| `HUB_MCP_SERVERS_FILE` | 指向 `~/.hub-agent/hub-mcp.json`，里面是 `{"mcpServers": {"enterprise-hub": {…}}}`（嵌套桥） | 把条目并入底层 agent 的 MCP 配置，让应用里的 agent 用知识库、技能、出图出视频；校验字段、不覆盖应用自己的 `playwright`、最多 8 个、文件不超过 64 KB |
| `HUB_TRACE_ID` | 本次「打开应用」的追踪 ID | 应用里发起的中枢调用沿用它，与打开应用落在同一条审计链路 |
| `HUB_CAPABILITIES_FILE` | 依赖预检结果（13.7 节），schema 1，不含密钥 | 每次使用时重读；仅当 `capabilities.browser.ready === false` 时拒绝**浏览器类**任务（409，写明缺什么与第一条处理方法），其余功能不受影响 |
| `HUB_WORK_OUTBOX` | 本机 outbox 文件路径 | 在关键产出变化时追加一行 JSON（`key`、`title`、`kind`、`status`、`progress`、`link`、`note`）；只写标题 / 状态 / 公开链接，**不写正文、提示词、账号资料、本机路径** |

## 14.3 中枢技能与应用手册：叠加而不是替换

小红书运营工作台自带详细的操作手册（`playbooks/*.md`：选题、对标、文案、封面、评论、复盘、发布、浏览器与账号安全），中枢又有主管维护的运营技能。两者**分工不同**：

| | 中枢技能（`read_skill`） | 应用手册（`playbooks/`） |
|---|---|---|
| 管什么 | **业务标准**：口吻、选题标准、合规红线、回复原则、复盘指标 | **怎么在工作台里做**：文件位置和格式、检查点、受控任务的输入输出、浏览器与账号安全 |
| 谁维护 | 公司主管 / 老板（中枢控制台，有版本和审核） | 工作台开发（随工作台版本发布） |

叠加的做法：

- 每个手册开头有一行「中枢技能」，写明对应的公司技能（选题 → `xhs-topic`，对标 → `xhs-breakdown`，文案 → `xhs-writing` + `xhs-compliance`，封面 → `xhs-cover`，评论私信 → `xhs-comment`，复盘 → `xhs-review`，发布前检查 → `xhs-compliance`）；
- 普通对话任务的提示词（`prompt.mjs` 的 `hubGuidance`）要求 agent 做那个模块前先 `read_skill`，同一会话读过不重复读；
- **优先级**：文件格式、存放位置、检查点、浏览器与账号安全、**不自动发布**，以手册为准；业务标准以公司技能为准；
- **直接冲突时，agent 先停下来说明，不要自己挑一个**，并对中枢技能提改进建议（8 章）；
- **读不到中枢技能**（没接中枢、没权限、失败、任务没有中枢工具）时，只按手册做，不重试，也不中断；
- 受控任务和只读采集任务没有中枢工具，不加这段指引；没接中枢时提示词与以前完全一致。

这个设计避免了两个风险：只用中枢技能会丢失手册里的操作细节（写错一个字段工作台就出错）；只用手册则主管改了业务标准、工作台不知道。运营部的七个技能就是从手册里提炼业务标准重写的（原来只有 4 步通用模板），中枢技能里**不写文件格式和操作步骤**（6.4 节）。

## 14.4 工作台里的权限与红线

- **自动化只能只读分析，不能自动发布**：这是公司的硬性要求，体现在手册、提示词和代码里。发布由员工本人在官方应用完成，工作台只做本地准备、预览、下载和提醒。
- **两档浏览器权限**：只读档（默认）禁用 14 个写类 Playwright 工具，只留打开网址、快照、截图、等待、查找、标签页等读取类；测试档放开点击输入但仍禁用上传文件和执行脚本，并屏蔽创作者中心（发布入口所在）。测试档需要用户明确授权，测完切回。
- **能力预检不拦打开**：缺 CodeBuddy CLI、浏览器等只让浏览器类功能不可用，写笔记、看数据等照常。

## 14.5 已验证与已知限制

已验证：真实的 CodeBuddy CLI 2.171.0 按手册读取中枢技能并按标准产出；用户口头声称业务标准变化时不照单全收，确认后提交带完整内容的改进建议；工作台产出经 outbox → 接入器 → 中枢，在真实环境里幂等写入并在看板显示。

已知限制（接第二个应用前要先处理）：接入器 `launch_app` 里写死用 `node` 启动，`requires` 只能声明有限的几种能力；里面还有工作台的特例（找 `SKILL.md`、判断「尚未配置」）；`HUB_MCP_SERVERS_FILE` 只对 Claude Code 生效，CodeBuddy 靠全局配置；应用自带的模型密钥（生图、视频）还没统一到中枢；工作台自己的知识库和中枢知识库是两套。这些都记录在接入指南的「当前的限制和待办」里。
