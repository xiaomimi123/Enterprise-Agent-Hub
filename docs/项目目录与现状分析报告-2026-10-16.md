# 企业智能体中枢：目录与现状分析报告

日期：2026-10-16。范围：当前仓库目录、说明文档、主要实现、部署配置及本地测试。检查前 Git 工作区干净，最近提交为 `ec7c9ef`。本次未启动或变更 Docker 服务，未调用真实模型、GPU 或企业身份服务；文档中的历史联调记录不等于本次实测结果。

## 1. 总体判断

这是面向约 50 人企业的 AI 助手管理中枢，已经具备可演示的工程原型。它的主要价值是统一身份、按岗位授权、按员工计量，以及跨模型和工具调用的审计，而不是训练模型或自研完整员工端 Agent。

当前适合继续做真实环境联调和小范围试点；仅凭现有代码和测试，还不能认定达到正式生产交付标准。README 标注“阶段 0 五步完成”，应理解为最小链路验证完成，其中模型和 GPU 的演示包含模拟服务，RAGFlow 本体仍待实机验证。

仓库有 127 个 Git 跟踪文件；技能目录包含 17 份 SKILL.md，知识目录包含 11 份业务示例 Markdown（两者均不计各自 README）。业务样例明显围绕美妆、小红书运营展开，其他部门提供基础岗位模板。

## 2. 目录职责与架构

| 目录 | 实际职责 | 判断 |
|---|---|---|
| `console/frontend/` | React、TypeScript、Ant Design、ECharts 管理端 | 已实现总览、成员、岗位包、技能、知识、审计、用量共 7 个页面 |
| `console/backend/` | FastAPI API、身份鉴权、权限、模型代理、MCP、GPU 调度与持久化 | 项目的核心业务代码；目录名比实际职责窄 |
| `hub/` | Docker Compose、数据库初始化、环境生成、启动命令与 RAGFlow 安装 | 部署与集成层，不是业务代码中心 |
| `agent/` | 登录、领取配置、同步技能、启动 Hermes | 286 行接入脚本；并非独立开发的完整 Agent |
| `gpu-node/` | ComfyUI 节点说明、Windows 搭建任务书、工作流 | 当前只有一个小红书封面工作流；视频生成尚未实现 |
| `skills/` | 各部门岗位技能文本 | 可维护的内容资产，不等于每个技能都配有独立执行服务 |
| `vault/` | 企业知识 Markdown 与目录结构 | 示例知识源；检索范围由后端注册表和岗位权限决定 |
| `docs/` | 方案、演示、部署、接口设计、决策记录 | 文档覆盖较好，但部分状态描述已经滞后 |

主要调用关系：

```text
管理员 → Web 控制台 → console-api → Casdoor / PostgreSQL / New API

员工 → hub_agent.py → Hermes
                       ├─ 模型调用 → console-api /v1 → New API → 模型渠道
                       └─ 工具调用 → hub-mcp → 岗位权限 → 知识 / 技能 / GPU 队列
                                                                    ↓
                                                        hub-worker → ComfyUI

模型与工具事件 → audit_events → 按 trace_id 聚合展示
```

控制台 API、MCP Server 和 GPU worker 共用后端镜像，但以不同进程运行。GPU 队列实际保存在 PostgreSQL，不是 Redis 队列；Redis 在当前 Compose 中服务于 New API 等基础组件。

## 3. 已实现能力与边界

| 能力 | 代码中的实现 | 仍需验证或补齐 |
|---|---|---|
| 身份 | Casdoor OAuth、JWT 校验、组织管理员访问控制 | 真实钉钉登录、组织同步及离职撤权闭环 |
| 岗位权限 | MCP 每次调用解析岗位包，过滤技能、知识库和生图工具 | 多部门归属规则、权限变更失败反馈、停用行为 |
| 模型管理 | 每人专属 key、模型白名单、额度下发、统一代理 | 高调用量下额度正确性、并发更新、真实渠道验收 |
| 审计 | 模型和 MCP 共享 trace，记录 token、检索和生图事件 | 并非员工所有本机操作的完整审计；身份平台登录事件仍待并入 |
| 知识 | 本地检索、RAGFlow 客户端与灌库脚本、异常回退 | 真实 RAGFlow 解析及召回效果、知识更新流程 |
| GPU | 持久化队列、节点状态、工作流提交、结果下载签名 | 实卡效果、异常恢复、并发调度约束、视频输出 |
| 员工端 | 独立 Hermes 配置、工具开关、确认策略、写入安全根环境变量 | 本机限制依赖 Hermes 实际行为；本仓库未包含其实现或完整隔离验证 |
| 外部智能体 | 区分应用身份，按岗位与知识库设置限制读取 | 真实第三方客户端互操作验收 |

岗位包和知识注册表仍包含固定部门、固定业务标识。适合单企业试点，但多客户交付需要把这些映射配置化；不能因为数据表有 org 字段就认定已实现完整多租户产品。

## 4. 优先问题

### 高优先级：云部署 HTTPS 文档与 Compose 不一致

位置：`hub/docker-compose.yml` 的共享 environment、`docs/部署清单.md` 的形态 B。

文档要求在 `.env` 中配置 `CONSOLE_PUBLIC_URL`、`HUB_MCP_PUBLIC_URL` 和 `HUB_COOKIE_SECURE=true`。但 Compose 前两项直接拼成 `http://${HUB_HOST}:...`，没有透传 `HUB_COOKIE_SECURE`。仅按文档改 `.env`，不会改变这些容器设置。

影响：反向代理有 HTTPS，服务仍可能生成 HTTP 登录回调、模型入口、MCP 地址和结果链接，cookie 安全属性也不会按文档启用。需要让 Compose 显式接收公网 URL 与 secure 配置，并验收完整登录及员工接入链路。

### 高优先级：月额度重算依赖有上限的日志列表

位置：`console/backend/app/newapi.py::logs`、`entitlements.py::month_used_quota` 和 `apply_model_limits`。

日志读取默认最多 50 页 × 100 条，即 5,000 条。月消耗按这批日志筛选员工后求和，再写回剩余额度。超过上限时，未读取部分的消费会漏计，可能把剩余额度写得偏高；控制台成本统计也会不完整。

建议使用完整分页或服务端聚合，并加入超过 5,000 条消费日志的验收案例。同时检查每个员工反复读取全量日志的开销，以及消费中更新额度的并发行为。

### 高优先级：真实模式仍可能显示演示数据

位置：`console/backend/app/providers/casdoor.py`。

`CasdoorProvider` 继承 `DemoProvider`，先载入演示数据，再替换部分字段。没有 GPU 节点时 `_sync_gpu()` 直接返回；模型网关未配置或首次读取失败时，用量同步也直接返回，因此相关演示数据可能保留。服务状态等字段也需要逐项确认真实来源。

影响：界面可能出现看似真实的节点、费用或健康状态。建议生产模式从空状态初始化，明确区分“未配置”“读取失败”“缓存过期”和“演示”，不要静默保留样例值。

### 中高优先级：GPU 故障恢复与多 worker 安全性不足

位置：`console/backend/app/db.py::claim_task_for`、`gpu.py::_dispatch`、`_collect`。

领取任务与写入 ComfyUI prompt_id 之间存在中断窗口。如果进程在此期间退出，任务已经 running，但没有 prompt_id；收集逻辑会一直跳过它，该节点又会被视为忙碌。持续返回 running 的任务也没有执行总时限。

此外，“检查节点是否忙碌”和“领取任务”是分开的数据库操作。SKIP LOCKED 能保护任务领取，但不能单独保证两个 worker 不向同一个节点各派一个任务。当前 Compose 只有一个 worker，多 worker 风险主要影响后续扩容。

建议补充任务租约、超时、重启恢复及提交幂等性，并将节点占用检查纳入原子约束。MCP 的 90 秒是调用等待时长，不是后台任务执行上限，文档应区分两者。

### 中优先级：权限变更的“立即生效”不能一概而论

位置：`providers/casdoor.py::_push_entitlements`、`entitlements.py::resync_all`、`mcp_server.py::_principal`、`agent/hub_agent.py`。

MCP 会重新读取岗位包；模型额度由管理操作推送到网关，推送失败被捕获并交给约 10 分钟巡检重试；员工本机配置在同步或启动对话时更新。部门信息则取自令牌 claims 或已记录的 presence，组织变动不是即时重新查询。

因此，需要分别说明知识工具权限、模型权益和本机策略的生效时机，并给管理员反馈推送失败。离职、调岗、撤销旧令牌和模型 key 的联动回收需要单独验收。

## 5. 工程质量与本次验证

优点：职责模块较小，鉴权、权限、模型代理、GPU、知识检索有独立文件；前后端依赖有锁文件；提供 Compose、初始化脚本、模拟服务、冒烟脚本和测试；文档已考虑客户部署与演示流程。

本次实际执行：

| 检查 | 结果 |
|---|---|
| 后端 `.venv/bin/python -m pytest -q` | 39 passed，0.70 秒 |
| 前端 `npm run build` | TypeScript 与 Vite 构建通过 |
| 前端 `npm run lint` | 退出码 0；EChart.tsx、auth.tsx 共 2 条 Fast Refresh 警告 |
| 前端包体积 | 主 JS 约 2.34 MB，gzip 约 764 KB，触发超过 500 KB 提示 |

这些结果说明现有本地测试通过、前端可构建，不代表真实外部组件或完整部署已经通过。本地测试大量使用替代对象，GPU 并发、进程崩溃恢复与真实数据库集成仍需专项验证。仓库未见 CI 工作流；数据库目前通过启动时建表初始化，未见独立版本化迁移体系。

文档还应统一以下口径：`console/README.md` 仍称用量与 GPU 为演示，但代码已能接真实数据；`hub/README.md` 表格仍称 RAGFlow 尚未接入，而客户端已实现；部署清单称“GPU 节点页”，实际前端没有独立 GPU 路由，节点展示在总览相关组件中。

## 6. 下一阶段建议

1. 先修交付可信度：HTTPS 参数、真实模式演示数据残留、额度日志截断、权限推送失败反馈。
2. 完成一套真实业务验收：真实员工登录 → 真实模型 → 查授权知识 → 实卡出图 → 审计与消费核对；同时跑越权、停用、额度清零和离职撤权案例。
3. 补可靠性：GPU 卡死及重启恢复、数据库迁移、备份恢复演练、日志保留与服务健康检查。
4. 再扩功能：员工安装与更新、更多岗位工具、视频工作流。现阶段无需为了目录结构先拆成大量微服务。

建议试点验收线：真实数据不混演示数据；权限与额度可验证地生效；任务故障可恢复；管理员能够从审计解释一次请求的结果与消耗。达到这些条件后，再扩大员工使用范围。
